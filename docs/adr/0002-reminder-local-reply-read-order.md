# 本机回复按读取先后归属提醒计数，打开串时推进基线

全串更新与 PO 追更沿用 [ADR 0001](./0001-reminder-reply-count-baseline.md) 的回复数基线，后台检查仍只读各模式第 1 页。本机确认的回复不再靠第 1 页的序号定位，而是用两次读取夹住它：一次读取完成于发送意图持久化之前，所得回复数不可能包含该回复；另一次读取的同一响应中能看到该回复，所得回复数必然包含它。该回复因此落在两数之间，扣数时只扣它本身，无需知道它的序号，删除留下的空位也不影响判断。用户打开串时，计数清零，同时按应用这次实际读到的最新回复数推进对应模式的基线，使计数与“自上次打开该串以来”的定义一致。

这样做是为了让长串也不提醒用户自己的回复，同时不按串长度或检查频率增加请求：证明通常来自发送后跳到自己回复时的那次读取；额外请求只由用户自己的操作触发。

## Considered Options

- **第 1 页序号定位（v1.1.0）**：不增加请求，但只覆盖前 19 条回复，长串基本无效。
- **逐页补读以恢复序号**：受控实验表明，删除留下的空位不出现在页面上，读完所有可见页也无法区分归属，而且请求量随串长增长。
- **发帖后把基线加一或跳到最新回复数**：会吞掉同时到来的他人回复。

## Consequences

- 发送后若应用没有读到包含该回复的页面，下次检查对该串该模式补读 1 页：发送前所知回复数之后紧接的那一页，通常就是当时的末页。该页仍看不到该回复时照常提醒。每条本机回复至多补读一次。
- 打开开了 PO 追更的串时，若这次打开没有读到 PO 页，会补读 1 次 PO 第 1 页。该请求走后台通道，遵守现有的间隔与限流退避；同一串只排队一次，未读成则不推进 PO 基线。
- 只有用 PO 饼干发出的回复才计入 PO 计数，因此只有这类回复需要在 PO 模式扣数。
- 有一种情况仍会提醒自己：发送期间恰有后台检查读取第 1 页，且在取得“看得到该回复”的读取之前，用户已打开该串清零。这时无法判断该回复落在清零前还是清零后，宁可多提醒一次自己，也不扣他人。
- 其他客户端或网页发出的回复没有本机发送记录，仍不排除；不按饼干 ID 抵扣。
- 读取先后按本机持久化的顺序判断，不依赖论坛时间与本机时钟的对比。
