# 降级时恢复升级前备份，而不是让旧版写新结构

汐岛在需要迁移数据库时，先保存一份升级前备份（数据库与 `draft-images/`，不含图片缓存），只保留最近一份。较旧的版本打开较新结构的数据库时仍然只读，横幅先建议改用新版；用户也可以明确选择恢复升级前备份，放弃升级之后的改动，然后应用重启。以后的迁移不必与旧版兼容，只有秘密表的表名和键列须保持稳定。

这样做是因为已有迁移中删表、删列、改列名、重建表和改写数据都出现过，旧版直接写新结构并不安全；如果要求以后的迁移只做加法，这条约束就要一直背下去，旧版写入时也不会维护新版新增的不变量。应用内更新不会降级，降级只发生在用户手动安装旧版时；最常见的情况是新版出问题后退回上一个版本，一份最近的备份足够应付。

## Considered Options

- **前向兼容（旧版可读写新结构）**：要求以后的迁移只做加法，与已有迁移历史不符，约束也无法撤回。
- **保持只读，只改进提示**：已作为降级时的第一选择保留，但用户只能靠手动恢复备份继续用旧版。
- **按结构版本保留多份备份**：可以跨多个版本降级，但磁盘占用会不断增长，这种场景也少见。

## Consequences

- 只对包含本机制的版本生效；更早发布的版本降级后仍然只读，需要按文档手动恢复。
- 备份失败时不迁移，应用进入存储不可用状态；用户可以重试，也可以明确选择“不备份继续升级”。后者原地迁移，数据保留，但之后无法回到升级前。
- 备份比当前程序新时，不提供恢复，只给手动说明。
- 恢复确认框写明备份时间和备份来自哪个版本，并按类别列出会丢失的改动，不精确比较差异，因为那样需要旧版理解未来的结构。
- 恢复时不带回用户已删除的秘密：备份中的饼干凭据按本地编号、App UUID 按 `id`、官网登录会话按当前是否存在，只保留当前库中仍有的。因此以后的迁移必须保留 `credentials`、`subscription_app_credentials`、`account_session` 的表名和键列；旧版读不懂时，恢复时去掉全部秘密，提示用户重新导入。
- 被替换下来的较新数据库另存为“降级前数据”，不删除，下次恢复时覆盖，文档说明怎样手动换回。
- 降级期间一直只读的数据库，再升级时直接照常打开；恢复过备份的，再升级时重新迁移，迁移前另做备份。
- 缺失的图片缓存文件按没有本地文件处理，所以备份不包含图片缓存。
