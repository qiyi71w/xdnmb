# 开发与维护

面向参与开发和发布的维护者。使用说明见 [README](../README.md)。

## 环境与命令

需要 Node.js 24 LTS 与 npm（版本见 `.nvmrc`；`.npmrc` 启用了 `engine-strict`）。

源码注释直接说明行为与约束，不依赖未公开的规格章节编号；需要交叉引用时，指向仓库内的公开文档或源码。

```bash
npm ci            # 安装锁定依赖
npm run dev       # 开发模式（热更新）
npm run build     # 构建到 out/
npm start         # 运行构建产物
npm run typecheck # 主进程、preload、共享代码、界面与统计服务的类型检查
npm test          # Vitest，运行在 Electron 自带的 Node 中，与应用使用同一 SQLite 驱动
npm run dist:win  # 在 Windows 上构建 x64 NSIS 安装程序与 latest.yml 到 dist/
npm run dist:mac  # 在 macOS 上构建 x64／arm64 DMG 与 latest-mac.yml 到 dist/（DMG 由 hdiutil 生成，只能在 macOS 上构建）
npm run analytics -- serve  # 本机运行使用统计服务（配置见 docs/analytics-service.md）
```

## 打包与发布

打包配置见 `electron-builder.yml`：使用上游预编译 Electron，不编译 Chromium／Electron／Node；better-sqlite3 自带各平台的 N-API 预编译模块，打包时不需要编译原生代码。只打包 `out/`、`resources/icons/`、`package.json` 与 `LICENSE`。版本号取自 `package.json`；发布时把安装包与对应的 `latest.yml`（Windows）、`latest-mac.yml`（macOS，两种架构合在一个文件里）一起上传到 tag 为 `v<版本>` 的正式 GitHub Release，客户端依赖这些文件名与其中的 SHA-512。

GitHub Actions 有四个工作流。`.github/workflows/ci.yml` 的 `check` 在 Ubuntu 上依次运行类型检查、测试和生产构建，每个 PR（包括只改文档的）及推送到 `main` 时都会运行；`main` 受规则保护：只能经 PR 合并、保持线性历史、禁止强推和删除，`check` 通过才能合并，管理员也不例外。两个打包工作流在 PR、推送到 `main` 及手动触发时运行；只改 `README.md` 或 `docs/` 时跳过，它们的结果显示在 PR 上，但不是合并的必要条件。Dependabot 每月检查一次 Action 版本；npm 依赖仍手工升级。

`.github/workflows/release.yml` 在推送 `v*` tag 时运行：先确认 `package.json` 的版本号是稳定的 `major.minor.patch`（客户端不接受预发布版本），且 tag 等于 `v` 加该版本号；再调用两个打包工作流，对 tag 指向的提交完整构建和检查两个平台的安装包，全部通过后把三个安装包与 `latest.yml`、`latest-mac.yml` 上传到同名的草稿 Release。草稿对客户端的更新检查不可见；填写说明并正式发布仍由维护者手动完成。已正式发布的 Release 不会被重新上传覆盖；重跑时，同名草稿中的文件会被替换；上传前若 tag 已改指其他提交，这次运行不上传。重跑失败的打包作业时，新产物替换上一次尝试留下的同名产物。

`.github/workflows/macos-packages.yml` 在 GitHub 的 Apple Silicon macOS 机器上运行类型检查和测试，构建两种架构的 DMG，再用 `scripts/ci/mac-update-smoke.mjs` 检查：两个应用的 CPU 架构与 SQLite 原生模块、应用身份、图标、临时签名、`latest-mac.yml` 中的 SHA-512；Intel 版在 Rosetta 下能启动并读写数据；Apple Silicon 版安装后，用只在更新网络会话内应答的受控发布源走完缺少元数据时检查失败（不显示为已是最新）、发现新版、校验失败丢弃、自动下载、打开 DMG、退出、按用户方式替换应用、下次启动显示新版本并保留设置。每次启动后先在首次第三方服务弹窗仅打开“软件更新”开关并“保存选择”，搜索与统计保持关闭；当前公告标为“不再提示”，之后的检查不会被这些对话框遮挡。结果不依赖仓库实际发布了哪些 Release。DMG、检查记录和应用输出作为工作流产物保留 14 天；只有经 `release.yml` 调用时，DMG 才会进入草稿 Release。这些是自动化检查，不包括 Gatekeeper 首次打开提示与钥匙串授权等需要真人操作的环节。

`.github/workflows/windows-packages.yml` 在 GitHub 的 Windows x64 机器上运行测试，构建 NSIS 安装程序，再用 `scripts/ci/windows-package-smoke.mjs` 检查：`latest.yml` 中的 SHA-512、`xidao.exe` 与 SQLite 原生模块的 CPU 架构、版本资源中的产品名与版本、内嵌图标与 `resources/icons/xidao-icon.ico` 一致、固定的更新来源；随后为当前用户静默安装到新目录（以小写盘符给出，目录名含空格、中文、`~` 与方括号），确认卸载登记和开始菜单快捷方式，从这一写法的路径用独立数据目录启动已安装的应用，检查存储可写、系统密钥保护（DPAPI）可用、按 Windows 方式更新，保存一项设置并在重启后读回，最后静默卸载并确认文件、登记和快捷方式已移除。启动提示的处理与 macOS 相同。安装程序、检查记录和应用输出作为工作流产物保留 14 天；只有经 `release.yml` 调用时，安装程序才会进入草稿 Release。这些检查不包括更新链（发现、下载、退出时安装新版），也不包括 SmartScreen 提示、为所有用户安装时的管理员授权等需要真人操作的环节。

### 阅读导航与列表记忆

`features/tabs/readingNavigation.ts` 集中处理引用、本机搜索命中、发送后定位、列表目标与历史记录的打开。调用方先取得来源，再提交打开意图；返回值区分原位显示、已提交历史／新标签、列表选择和过期拒绝，不把 `dispatch` 当作同步成功。定位请求、取消代次、引用卡片、搜索会话和发送后刷新仍由各调用方管理。

`tabsReducer` 保持标签与历史的唯一状态来源。导航 reducer 只计算状态与提交回执；提交后的 effect 再触碰阅读器、完成 Promise 和确认回执。同批导航串行处理，前一条改变历史后，后一条必须重新验证来源；引用额外校验来源串，防止分栏列表在相同历史 key 下切串后接受迟到结果。发送使用开始时的阅读快照，空快照沿用当前阅读器回退，保留阅读器实例和普通历史语义。

进入延迟导航时仍须检查调用方的有效性：引用与本机搜索核对最新活动标签，不依赖稍后的关闭 effect；提醒列表把点击代次与挂载状态检查传到导航处理阶段，较新的点击可撤销已经排队的目标。否则分栏中不改变历史 key 的选择，不能单靠来源 key 排除迟到结果。

同列表的新历史步骤通过 `ListMemorySeedsContext` 在首帧提供完整列表记忆，`useInitialListMemory` 在 layout effect 中落入 registry；父回执不会覆盖子视图已经更新的记忆。新标签不继承来源列表记忆。reducer 和 render 均不修改 registry Map，也不执行 DOM 操作。

回归检查从 `source/open` 驱动生产 reducer，覆盖过期来源、同 key 切串、同批提交、重放、拒绝无副作用、首帧记忆及发送快照。真实 React StrictMode 挂载另核对首帧种子和子视图更新优先。Linux Electron 已用生产 renderer／preload、隔离数据目录与受控 IPC 走查引用／搜索／发送／历史打开、返回与列表连续性；受控发送不访问论坛，此证据不替代主进程网络／存储验证或 Windows／macOS 原生验收。

## 数据与安全实现

- 本机数据保存在 Electron 用户数据目录下的 `xidao.sqlite`，由主进程中的单个数据库 worker 访问（WAL、外键、短事务）。数据库结构单向升级；升级失败时回滚并保留原文件，不删除或重建数据库。用较旧版本打开由较新版本写入的数据库时，只用只读连接读取并拒绝写入（此时也不能导入、重命名、移除饼干或修改用途），数据库文件和 WAL 保持逐字节不变；降级时的恢复见“数据库迁移 › 降级与恢复升级前备份”。退出时若本次运行的存储只读或不可用，不保存工作区直接退出，下次启动恢复此前保存的工作区，这次退出也不安装更新（与草稿未保存时仍退出相同）；存储可写而单次保存失败（如文件被其他程序锁住）时仍停在退出流程，可重试或取消退出。
- 阅读模式、阅读位置、访问记录和设置是个人记录，与缓存的论坛内容分开保存，不依赖缓存内容存在。汐岛不提供串收藏，也不记录已读／未读：没有首条未读、全部标为已读、未读数或“仅未读”筛选，订阅列表不显示新回复，追更请开启提醒。收藏版块（图标栏首字入口与版块管理）不受影响。自己的发言、PO 饼干与引用我的发言都只按饼干 ID 识别，不另存发言库。
- 受保护内容：离线副本保存的发言、草稿目标串和当前阅读的串，以及每条访问记录所在串的主帖文字和最近一次“全部”回复数（[ADR 0004](adr/0004-visit-records-protect-head-text.md)）。它们计入“受保护内容”，不计入普通缓存额度，不被容量淘汰或“清理普通缓存”删除；受保护总量超过上限时显示已有的提示。访问记录不保护缩略图、原图和该串其余页与回复；淘汰该串缓存页时回复数单独留下。主帖仍留在本机搜索索引中。删除单条访问记录或清空历史成功后，这两项转为普通缓存并立即检查一次额度（删除失败不检查）；仍被离线副本、草稿或当前阅读保护的照旧。失去保护的回复数作为普通缓存参与淘汰，先于它引用的主帖删除，不会残留。
- 读取到的图片保存在用户数据目录下的 `images/` 中，文件名由应用生成，数据库记录每个文件是缩略图还是原图、来源地址、取得时间、实际格式与尺寸，缩略图与原图分别记录。同一图片被多条发言或多个标签使用时只保存一份。
- 图片先完整写入临时文件，校验后改名到位，再提交数据库记录；中途失败、取消或写库失败时，已有的文件和记录保持不变，新文件被删除。正在显示图片的阅读视图会保护所用图片不被清理；清理只删除没有任何保护的记录及其文件，不会删除 `images/` 以外的文件，也不跟随符号链接。每次启动时会移除上次中断留下的临时文件和没有记录的文件。界面通过应用自己的 `xidao-image://` 地址读取这些文件，不暴露文件路径。
- 引用预览卡片按卡片 ID 独立持有图片视图，复用正文缩略图与原图查看器。查看原图时固定引用卡片并暂时隐藏、禁用它，Esc 先关闭原图并回焦缩略图，再关闭卡片并回焦来源；切换引用、关闭卡片或来源标签失效时取消旧读取并释放图片保护，迟到结果不会进入新卡片。
- 图片遮罩采用磨砂模糊，保留图片色彩、弱化细节，不改变下载、缓存、离线保存或复制原图。设置 › 阅读提供开关（默认关闭）和 0–100% 模糊强度（默认 100%，最强模糊），经现有设置校验与 SQLite 持久化；强度为 0% 时图片清晰，单击直接打开原图。滑杆旁的内置示例图随输入即时更新，保存仍按既有设置输入延迟合并。正文、串列表、引用卡和设置预览复用同一磨砂层，模糊半径随图框宽度与强度变化；编辑中的附图和原图查看器不遮挡。
- 揭开状态只保存在当前标签的本次页面浏览中，同页同一发言的缩略图共享状态；切换串、页面或标签，以及单栏阅读器／列表切换导致原区域离开屏幕时，重新遮挡并关闭已打开的阅读原图查看器。同串滚动、加载、刷新、只看 PO、关闭原图或引用卡不清空状态；关闭后重新开启遮罩、或模糊强度从 0% 调回正数会清空所有揭开状态。遮挡时首次点击或键盘激活仅揭开，再次激活打开原图；磨砂效果仍透出图片色彩，不是隐私保护或内容过滤。
- 普通缓存的图片在超过额度或手动清理时按上面的规则删除；受保护（正在显示、离线副本引用、草稿副本）的图片不会被删除。
- 版规图片：目录读取时从 `getForumList` 的 `msg` 里取出最多 4 个 `<img>` 地址（`rulesImages`，随目录快照保存；正文节点仍丢弃 `img`）。只接受公开主机名的 https 地址，`http:` 一律改为 https 请求，拒绝 IP 字面量、单标签名与 `localhost`、带端口或凭据的地址。界面只在展开版规时按“版面 ID + 序号”请求，主进程从本机目录快照查地址，用单独的下载器（`allowedOrigins: 'public-https'`）读取：主机名只解析一次，解析结果中只要有一个非公网地址就不连接，连接只使用这次检查过的地址。IPv4 排除本机、私网、共享（CGNAT）、链路本地、文档、已弃用的 6to4 中继任播 `192.88.99.0/24` 与保留段；IPv6 按白名单判断，只有全球单播 `2000::/3`（去掉 `2001::/23`、`2001:db8::/32`、6to4 `2002::/16`、`3fff::/20`）和 NAT64 `64:ff9b::/96` 算公网，NAT64 地址再按其中嵌入的 IPv4 地址套用上面的 IPv4 规则。与论坛图片一样不带 Cookie、饼干或其他凭据，不跟随重定向，按内容判断格式与尺寸，作为缩略图类受管文件缓存并受阅读视图保护。图床会看到用户 IP；图床不可达时只显示“图片加载失败”与重试。
- 复制原图只针对查看器中已完整解码显示的原图：界面只传发言编号和该原图的 `xidao-image://` 地址，主进程核对它确是这条发言已取得的受管原图后自己确定文件与编码，不接受任意路径，不重新下载，也不以缩略图代替。复制期间对该原图另加临时保护，结束即释放，不改变阅读视图、离线副本或草稿对它的保护。文件以不跟随符号链接的单个句柄读取，按内容识别格式，并在无预加载、不能打开新窗口的隐藏沙箱页面中逐帧完整解码，尺寸须与文件头一致。
- 静态图写入完整解码后的 PNG 图像，保留透明通道，不缩放、不按窗口裁切。动图不转成静态图：原始字节复制到用户数据目录下单独的 `clipboard-images/`，再以文件 URI 列表写入剪贴板（Electron [`clipboard`](https://github.com/electron/electron/blob/v45.0.0/docs/api/clipboard.md) 与 [`ClipboardItem`](https://github.com/electron/electron/blob/v45.0.0/docs/api/clipboard-item.md) 的 `text/uri-list`，在 Windows／macOS 上对应系统文件剪贴板），接收软件可能把它作为文件附件。内容准备好后一次提交，不先清空剪贴板；原图未就绪、文件校验未通过、另一次剪贴板操作进行中或写入失败时如实说明，不报告成功。
- `clipboard-images/` 与图片缓存分开：关闭查看器、普通缓存额度或手动清理都不会删除其中文件，退出、重启后剪贴板仍引用的文件继续保留。主进程在启动时、此后每 30 秒、每次复制成功后以及退出时回收这个目录：只读取剪贴板中的文件引用（不读取文字或其他内容），保留仍被引用的文件，删除其余文件和中断留下的临时文件；剪贴板被其他内容替换后，旧文件在下一轮删除。回收不跟随符号链接，不触及 `images/`；剪贴板暂时无法读取或文件仍被占用时本轮不删除，留到下一轮。
- 草稿保存在数据库中：每份草稿只有一个保存版本，目标、饼干引用、文字字段与附图引用在同一事务中一起替换；保存失败时上一个保存版本保持不变。饼干引用不随饼干移除而改写，移除后显示为“已移除”。各串记住的发言饼干同样只保存本地引用。
- 附图由主进程通过系统选择框读取所选文件，先复制为同目录临时文件，按文件内容确认是 JPEG、PNG、GIF 或 WebP 并检查尺寸，再改名为用户数据目录下 `draft-images/` 中的受管副本；所选原始文件只读不改。源文件不可读、不是图片、尺寸过大、磁盘空间不足都会作为失败说明，不留下临时文件。界面通过 `xidao-image://draft/…` 显示副本。
- 副本在被已保存草稿、打开中的编辑、仍可撤销删除的草稿或发送中／结果不明的发送尝试引用时受保护；没有任何引用时删除记录与文件。每次启动先恢复发送尝试，再清理无引用副本及中断留下的临时文件；尚未自动保存的编辑及其附图不跨重启保留。结果不明尝试的附件不会被启动清理移除。
- 饼干 userhash 通过 Electron `safeStorage` 的异步接口加密后存入数据库（Windows 为 DPAPI，macOS 为钥匙串）；数据库只保存显示名称、公开的饼干 ID、本地编号与密文。系统保护不可用时（包括 Linux 在没有密钥环服务时的 `basic_text` 后备）拒绝导入，已保存的饼干保持密文、不能用于读取，不会改用明文保存。系统保护防的是数据库文件被直接读取，不能防住以同一登录用户身份运行的其他程序。
- 解密后的 userhash 只在主进程内存中使用：界面只能取得显示名称、饼干 ID、来源、导入时间和用途选择；粘贴内容只在导入时经 IPC 传入主进程一次，导入成功或关闭设置后清空输入框。饼干只附加在主进程发往论坛阅读、订阅和发布接口的请求上，不写入 Chromium 会话 Cookie，因此界面加载的图片、外部链接等不会携带它。
- App UUID 使用相同的系统密钥保护器，数据库中只有本地引用和密文；更换后保留旧引用对应的密文供固定操作核对及显式合并，常规查询不返回秘密或秘密片段。论坛接受任意文字作 App UUID（空值对应一个所有人共用的集合，论坛也把纯空格当作空值），汐岛只去掉首尾空白、要求 1–256 个字符（UTF-16 码元），按原样保存与发送并区分大小写；UUID 放在请求 URL 中，论坛对约 1000 个汉字的 URL 返回 414，256 字的上限留有余量。早期版本保存时已转成小写的值照旧可用。观察、配置代次、逐项意图／报告、同步基线及计划历史保存在独立表中，不随读取失败清除。
- 订阅普通刷新按集合与固定配置代次共用在途读取，离开页面不取消共享任务；显式停止只停止该次读取，不重试。最新读取任务、最后完整展示快照和成员证据分别消费同一份观察记录。完整性须由从第 1 页连续读到有效空页证明，旧记录中的 `valid_observation_json` 只表示可用页，不证明完整；因此旧部分观察不会在升级后变成未订阅的证据。展示快照不用于确认写入或推导同步删除，写入回读和同步执行前复核仍使用固定对象的新证据。
- 两端的远端订阅列表都把最新订阅放在最前，与串号无关；论坛没有调整顺序的接口，汐岛只能通过写入先后影响它。同步与合并的预览仍按各来源端列表从上到下排列；执行时按预览的逆序逐项写入，即每个目标端都从来源端列表最下面一项往上写，补上的串在目标端保持来源端的先后、排在最前。删除项沿用同一顺序。同步计划的条目按实际执行顺序保存，同步记录按此显示。执行前复核、意图先行、遇到第一个未确认条目即停止、不重投等规则不变；中途停止后再同步，剩余的串补在已补写的串之前，最终先后仍与来源端一致，不需要续传记录。
- 订阅排列（`subscriptionArrangement`：`remote`／`app`／`web`，默认 `app`）沿用 settings 表的逐项读写与校验：缺失或非法的存储值取默认，旧版本按已知键读取会忽略它，无 schema 变更。它只改变汐岛中的显示，不读写远端，也不触发对排列基准一端的读取：当前查看的一端不是排列基准且设置不是 `remote` 时，按排列基准一端在本机保存的最后一份完整快照（同一配置代次与对象引用）重排当前列表。两端都有的串按排列基准的先后；只在当前一端有的串跟在当前列表中它前面最近的一个两端都有的串之后，前面没有就排到最前，同一位置的多个串保持原先后。列表未读完时只排列已读到的部分，位置来自排列基准，后续页不会挪动已显示的行。筛选在排列之后应用，键盘巡航按显示顺序。排列基准一端没有完整快照（未配置、锁定或从未读完）时按远端原样显示，列表顶部说明需要先读完那一端。
- 批量取消订阅（订阅页“…” › 选择多个）是具名 IPC 操作 `subscriptions.removeMany`：参数为来源、期望的配置代次和 1–1000 个互不重复的串号，经主窗口主框架调用方校验与逐项运行时校验，非法参数走非法请求路径。它与单项写入、同步与合并、核对共用同一个写入互斥（忙碌返回 `busy`）；代次不符返回 `stale`；任一串有未核对的写入时整批拒绝（`busy`），都不发请求。执行时按提交顺序（订阅页的显示顺序）逐项进行：每项取与单项写入相同的 `before` 证据，先持久化意图，再发一次取消请求，再保存请求结果；每发下一项之前检查是否已请求停止、配置上下文是否变化。某项的请求结果不是明确成功（被拒、结果未知、网络错误、限流或验证码）、用户停止或上下文变化时停下，其余项记为未执行，不留任何记录；发出的请求不撤回、不重试。至少发出一项且不是因限流停下时，从第 1 页连续读到结束候选回读一次（单次总时限 20 秒，不受停止影响），这份回读作为每个已发出项的 `after`，按单项写入的规则逐项判定；因限流停下时不回读，已发出的项都进入待核对。每项都是独立的订阅操作记录，不生成同步计划、不进入同步记录，之后的同步预览照常把确认取消的串识别为“在汐岛取消”。请求结果写库失败时保留已持久化的意图，重启后按孤立意图进入核对。返回逐项结果（已确认、结果不明、失败、未执行）与停止原因，订阅页据此在列表上方显示一行汇总；未执行的串保持勾选，结果不明的串显示核对入口。提醒、离线副本与阅读记录不受影响。
- 待核对操作的 `dismissedAt` 是独立的本地持久关闭时间，旧 JSON 缺字段时视为未关闭，不改变 schema 或历史报告。关闭事务成功后才解除该对象／串的待核对保护；失败保留原记录，运行中写入或核对拒绝关闭。关闭不访问远端、不删历史、不推导当前成员状态，后续写入仍须明确用户操作。
- 发送意图和结果由数据库事务保存；确认结果、实际发言身份、来源草稿删除在同一事务中完成。意图保存失败时不会发送；发送后的结果写库失败则保留原意图，界面说明可能已经发出，重启按未知处理。发送记录保存正文与身份的本地编号，不保存解密后的 userhash。退出时，已开始的发送只等到原本的 60 秒时限，结果写入本地存储后才结束进程。
- 串内发言次数（回复编辑框的饼干列表中的 `N 次`）只按本机发送记录统计：状态为已确认或论坛报告成功但串号未确认的发送（与历史“新串／回复”页相同），已确认的按记录的串号归串（新串即其主帖），串号未确认的回复按发送内容中的目标串归串，串号未确认的新串不属于任何串；发送中、结果不明和失败的不计。一条发送计给它所用的饼干，以及当前饼干 ID 与发送时记下的饼干 ID 相同的饼干，因此移除后重新导入同一饼干仍能接上；没有饼干 ID 的饼干只认本地编号。在官网或其他客户端的发言不计入，这个数不是该饼干在论坛上的发言总数。每次打开列表经具名 IPC `publication.threadPostCounts` 重新读取一次（参数串号走与其他串号相同的校验），不联网；读取失败时列表照常可选，另行说明次数读取失败。新串编辑框不读取。
- 引用我的发言提醒只计他人的新发言：新增页中经汐岛确认发出的发言（按发送记录里的发言编号），或饼干 ID 与任一已导入饼干 ID 相同的发言，即使引用了自己的发言也不计数，也不计为被引发言未能核实，检查不为它读取被引发言。判断只用本机数据，不新增请求；被引发言是否为自己的判定不变。
- 全串／PO 的本机回复排除按回复数的先后判断，不用第 1 页序号；后台检查每串每模式读第 1 页，只为待处理的本机回复按下文补读。每个串每个模式按数据库提交顺序（不比较抓取时间或本机时钟）保存一个观测：自回复数上次下降以来，已保存串页（阅读器、查找、离线保存、搜索收录与提醒检查读到的页面）中的最大回复数；基线都来自已保存的页面，因此包含在内。任一保存的页面回复数低于这个最大值即为一次下降：该模式所有待处理回复记为不可证明，之前的观测作废，从下降后的回复数重新累积，之后的新发送照常可以证明。持久化发送意图的同一事务中，为当时已开启的每个全串规则（以及发言饼干 ID 已知且等于主帖公开饼干 ID 时的 PO 规则）记下这个观测作为发送前回复数（没有任何观测时用基线；都没有则在该模式不可证明）。证明回复数是任一新鲜串页中能看到这条已确认回复时该页的回复数，取最小值：保存串页时记录，确认时（含后台与启动补确认）也查已保存的串页。未确认、结果未知和失败的发送不参与。基线覆盖到证明回复数后，在同一事务中按意图之后提交的区段判定一次：`(发送前回复数, 证明回复数]` 全被未清零的 `check` 区段覆盖时扣 1（可跨多段，抵扣记在最早仍有余量的区段上；跨多轮时只能证明合并计数应扣 1、不能证明属于哪一轮，较晚一轮的通知不因此被压掉，这种情况可能再提醒一次自己的回复，但不漏他人）；没有未清零的 `check` 增长（`open`、已清零或落在初始化基线内）时无需扣数；两者混合时不可证明。扣数、区段的已抵扣数与一次性处理状态同一事务提交，失败整体回滚；每条回复每个模式每个代次只处理一次，计数不为负，已清零的区间不抵扣之后的增长。规则关闭或再开启删除该模式的记录，新代次不处理意图早于它的回复。通知决策读取当前轮修正后的有效增长，已投递的通知不撤回；阅读器保存页面或打开时的 PO 读取证明回复后会刷新提醒列表。本机回复记录与回复数观测属于个人记录，不随普通缓存清理；缓存淘汰已保存的串页只会让证据变少。
- 发言后提醒引用我（设置 › 提醒，默认开）：汐岛的发送（新串或回复）转为已确认的同一事务中，为该串开启“引用我的发言”提醒，来源记为自动，到期时间为该次发送的意图时间加 7 天；论坛报告成功而串号未确认、结果不明的发送在之后确认时才开启，最终未确认的不开启。只开启“引用我”，不开启全串或 PO。该串“引用我”已由用户开启时不变；上次由用户在菜单里关闭时不开启；上次因取消订阅、同步删除或汐岛自己关闭而关闭的照常开启。已开启的自动规则再遇到确认发送只把到期时间后移（较早发送的迟到确认不会提前），不换代次、不清计数与已检查位置。设置关闭时不开启也不后移。用户在菜单开启的规则来源一律为用户、没有到期时间。网页或其他客户端的发言没有本机发送记录，不触发。
- 自动开启的“引用我”从自己那条发言之后开始：开启时直接把该发言记为已检查位置，首次检查照常先读第 1 页取回复数，再从起始页读到末页（第 1 页在范围内时复用）。起始页优先取本机已保存、含有该发言的“全部”页；否则按发送前回复数推算：持久化回复意图的同一事务把上文的“全部”模式观测（不论当时开着哪些规则）记在发送记录上，确认时不用之后读到的回复数代替；新串从第 1 页开始。开启后、首次检查前，阅读读取保存到含有该发言的页时，起始页改为该页（原本推算的起点更早或无从推算时）；到首次检查时仍无从推算的，与手动开启一样由首次检查定起点。请求形态、身份、每批 5 次与每轮 100 次额度和限流退避与手动开启的规则相同。
- 自动开启的“引用我”到期与关闭：到期时间按本机时间计，应用关闭期间照常流逝；到期本身不关闭规则，也不另设额度或调度优先级。到期后开始的下一次检查即最后一次检查，照常排队、读页并计数；它无覆盖问题地完成（串页与所需被引发言都读到，不是读取失败、未补完或被限流中断）时，规则状态记下这次检查的开始时间，同一事务中没有计数即关闭。没能完成时规则保持开启，留给下一轮。最后一次检查后仍有计数的，规则照常开启、照常检查，直到用户打开该串或在提醒页清除提醒后关闭；最后一次检查之前清零不关闭，仍等这次检查。关闭“发言后提醒引用我”时，与保存设置同一事务关闭所有没有计数的自动规则，不做最后一次检查；有计数的等清零后关闭。被引发言未能核实属于覆盖问题，不算计数，不阻止关闭。用户来源的规则与同串的全串／PO 规则都不受影响。上述关闭的原因都是汐岛自动关闭，沿用关闭语义删除该规则状态，不发应用内或系统提示；之后在该串经汐岛确认发送会重新开启。续期把到期时间后移，已完成的最后一次检查随之失效。
- 自动开启的“引用我”的请求开销与手动开启的相同：每轮检查每串先读第 1 页取回复数，有新回复时再读基线所在页到末页（第 1 页在范围内时复用），另加判断被引发言是否为自己所需的被引发言读取；没有新回复的串每轮只有第 1 页这一个请求。同时开着的自动规则只有最近 7 天经汐岛发过言的串，以及到期后仍有计数、等待清零的串，关闭后不再产生请求。
- 提醒页的行数据带每类规则的来源。“引用我”来源为自动时，行的元信息行右端显示“自动”标签（读屏名称“引用我的发言提醒为自动开启”），排在计数与覆盖问题图标之后；用户在菜单里开启后或规则关闭后消失。串内提醒菜单和其他列表不显示这个标签。计数、基线说明、警告图标与标签是一组：行宽不够时整组移到串号与回复数下方；更窄时计数只在种类之间换行，警告图标仍紧跟其后，标签仍在同一行右端；只有带缩略图的行窄到连“全串:128”、图标与标签都放不下一行时，标签才移到下方并靠右。
- 检查补读：某串某模式有已确认、待处理、已有发送前回复数、尚无证明且补读尚未发出的本机回复，并且基线自发送前回复数以来的上升全是未清零的 `check` 区段（补读找到它才可能扣数；已混入 `open`、已清零或未计数部分的区间无论如何都不可证明，不为它读页）时，检查读完该模式第 1 页、第 1 页回复数超过发送前回复数后，补读 `ceil((发送前回复数 + 1) / 19)` 页。候选限于本轮首次请求该串第 1 页之前已确认的回复（之后才确认的回复不一定计入该页回复数），并在第 1 页保存之后从数据库重新读取，第 1 页本身造成的下降或证明立即生效。该页是第 1 页时直接用已读的第 1 页判断，不再请求；同一模式有多条待补读回复时，本轮只读其中最靠前的一页，落在同一页的回复共用这次请求，其余留给后续检查。补读页能看到回复时，保存该页即记下证明回复数，并以补读页回复数作为本轮该模式的检查计数，区段覆盖整个区间，同一事务判定扣数；看不到时按第 1 页照常计数，这些回复在该模式记为不可证明。补读沿用提醒检查的后台通道、间隔、每串每批 5 次与每轮 100 次的请求额度、限流／验证码立即停止本轮（已读的第 1 页照常计数），身份规则与第 1 页相同（先匿名，被拒后用浏览饼干再读一次，两次请求都计入额度）。
- 补读机会的消耗：后台通道放行每个补读 HTTP 请求后，先在一个数据库事务中按上述条件重新判定这些回复，并把仍符合的标记为已发出（领取）；排队期间已提交的证明、打开吸收、回复数下降或规则换代次的回复在此排除，全部排除时不发请求、按第 1 页计数。这个领取事务是补读资格的串行化点。领取后若本轮已被取消（包括等待数据库回应期间），且这次补读还没有任何请求发出，就在数据库中撤回领取，下一轮再试；撤回失败作为存储错误上抛，不当作正常取消。未被取消时，在最后一次取消检查的同一同步步骤中把请求交给传输层，此后无论成功、失败、被拒或被取消都算用掉；同一次补读中已发出的匿名请求被拒后，用浏览饼干的那次重读，以及第 100 页之后的探测，仍属于这次机会，不另开新机会。额度不足或在排队中被取消的请求不会走到领取。HTTP 请求与 SQLite 不是同一资源，不存在跨两者的原子提交：进程在领取提交之后、请求交给传输层之前被强制终止时，这次机会会丢失，回复照常计数提醒（只会少扣，不会多发请求或误扣他人）。
- 请求上限：后台检查在没有待处理本机回复时仍为每串每模式 1 次第 1 页；每条本机回复每个模式最多增加 1 次补读页读取（被拒后用浏览饼干重读，或第 100 页之后的页附带的探测，各多 1 次 HTTP 请求，均计入额度），同一页上的多条回复共用。打开串只由阅读器自身的读取推进基线，开了 PO 追更且在全串模式打开时最多 1 次 PO 第 1 页后台读取；发送后跳到自己回复的读取是阅读器原有的读取，不额外增加。
- 阅读读取推进提醒基线：`reading.readThreadPage`／`reading.locateThreadEnd` 的请求必须带用途 `display` 或 `lookup`，主进程运行时校验，其他值按非法请求拒绝。阅读器显示该串的读取（打开时首次读取、翻页、刷新、末尾、发送后读取串尾）用 `display`；搜索结果、引用卡片与按串号打开前的“能否打开”读取用 `lookup`，之后打开的阅读器自己再读。只有 `display` 的新鲜网络读取，在保存该页的同一事务中把该模式已开启且已建立基线的全串／PO 规则推进到页面回复数；基线只升不降，不负责初始化（仍由提醒检查建立），也不清零或改变计数。主进程内部的引用预览与定位、搜索收录、离线保存、提醒检查自身，以及网络失败后显示的已保存页都不推进。引用我的发言提醒的已核对位置不随打开移动。
- 每个规则代次内，基线的每次上升按提交顺序记为一个区段：提醒检查计入计数的增长为 `check`（清零后标记为已清零，并保留本机回复的抵扣状态），阅读读取吸收的增长为 `open`（不计数、不清零）。检查轮开始后若阅读读取已把基线推高，该检查只计算超过当前基线的部分，较早读到的第 1 页不会把基线压低，后台检查请求数不变。
- 清零请求 `reminders.clear` 必须带来源 `open` 或 `manual`，主进程运行时校验，其他值按非法请求拒绝。打开串、切换到显示该串的标签、在串内跳转引用用 `open`；提醒列表的“清除提醒”用 `manual`，只把计数清零，不推进基线，也不读取任何页面。启动时恢复的标签不清零。
- 打开时的 PO 读取：`open` 清零时，若该串的 PO 追更已开启且已建立基线，主进程安排 1 次 PO 第 1 页读取，以与阅读读取相同的方式在保存该页的事务中推进 PO 基线（记为 `open` 区段，不计数、不初始化）。请求先等 1 秒并等阅读器同一串正在进行的 PO 页读取结束；实际发出前，若这次打开之后已有阅读器 `display` 用途的 PO 页保存（例如在 PO 模式打开），就取消。“这次打开之后”从主进程收到清零请求时算起，清零与规则查询仍在写库／读库时完成的保存同样计入；打开前的保存不取消这次读取；清零失败的请求不算打开，规则查询失败则不读取。请求走后台通道，与提醒检查共用串行和至少 1 秒的间隔；同一串在队列中只保留一个，已发出后再次打开会重新排队。限流退避期间不安排，进入退避时尚未发出的请求取消；应用退出时取消排队和进行中的请求。身份规则与第 1 页计数读取相同：先匿名，被拒后用浏览饼干再读一次，每次请求各占一个后台间隔。读取失败不推进基线；遇到限流或验证码时按提醒检查的规则进入或延长同一次退避，同一次退避只通知一次。论坛客户端在请求所占的后台槽位内完成响应判定（HTTP 429、验证码页、业务提示），提醒检查与打开读取的任一请求判定为限流或验证码时，在后台通道放行下一个请求之前生效：排在后面的打开读取不再发出；打开读取遇到时，正在进行的提醒检查（包括请求还在途时接受的手动检查）停止，尚未发出的检查请求不再发出，这次检查也不会清除刚进入的退避。之后再手动检查仍可执行，成功后照常结束退避。它不占用提醒检查每轮的读取额度，不触发 60 秒冷却、新一轮检查、上次检查时间或提醒通知。
- 界面页面启用 sandbox 与 context isolation，禁用 Node 集成与 webview，使用严格 CSP；不允许页面导航到其他地址或打开新窗口。权限仅为应用自己的主页面开放按需读取本机字体，其他权限均拒绝；官网登录窗口拒绝所有权限。界面只能调用少量具名操作，主进程校验调用页面（仅主窗口主框架中的应用页面）与参数，不提供任意网址、SQL 或文件访问。应用页面按其网址对应的文件路径识别，而不是逐字比较网址：Chromium 加载页面后保留 `~`、`[`、`]` 原样并把 Windows 盘符改为大写，而应用路径保持启动时的写法（小写盘符、8.3 短路径），所以应用装在这类路径下也能识别自己的页面；只有盘符不区分大小写，其余部分须是同一路径。路径含字面 `%` 的目录无法识别，应用会拒绝所有操作。
- 剪贴板只经两类具名操作：对发起请求的窗口执行剪切、复制、粘贴、全选之一，或写入应用给定的纯文字（复制串号、复制内容、复制饼干、复制选中文字，长度有上限）；以及上面的复制原图。界面不读取剪贴板内容，粘贴由主进程直接作用于焦点所在的输入框；剪贴板权限没有因此对页面开放。
- 应用只运行一个实例；再次启动会唤起已运行的窗口。

### 开机自启

- “开机时启动汐岛”直接读写系统登录项，不存进汐岛设置：设置页每次显示及窗口回到前台时重新读取，用户在任务管理器或 macOS 系统设置中的更改照实显示。切换后立即回读，系统报告的状态与请求不符时开关回到系统状态，并以底部通知“开机启动设置未生效”说明。“开机启动时后台驻留”是普通设置 `loginLaunchResident`（默认关），只属于本机；主开关关闭时禁用但保留取值。
- Windows 使用 Electron `app.setLoginItemSettings`，在 `HKCU\…\Run` 下以应用的 AppUserModelId（`appId`）为名登记安装后的 `xidao.exe` 并带上 `--xidao-login-launch`；写入时同时恢复任务管理器中的启用状态。读取以 `openAtLogin` 且 `executableWillLaunchAtLogin` 为开，任务管理器停用视为关。只有带该参数的启动算开机自启；应用自身重新启动时去掉该参数。NSIS 卸载时删除 Run 与 `StartupApproved\Run` 中的同名值，应用内更新（`--updated`）保留。
- macOS 使用 SMAppService 主应用登录项：只有 `status` 为 `enabled` 视为开。`requires-approval` 表示尚待允许，用户在“系统设置 › 通用 › 登录项”中关闭后也是这个状态，此时开关显示为关，并提示在登录项中允许、提供打开该页的按钮。开机自启由 `wasOpenedAtLogin` 识别。Electron 文档说明未签名／未公证的应用登录项可能静默失效，汐岛的 ad-hoc 签名下是否可靠须原生验证。
- 未打包的开发运行禁用这两项并说明“开发运行时不可用”，避免把 Electron 本身登记为开机启动；打包后的 Linux 没有登录项，不显示。
- 后台驻留启动：仅当本次是开机自启、存储就绪且设置开启时，首个窗口创建后不显示（与关闭窗口后选“后台驻留”相同）；存储不可用或只读时照常显示窗口。冷启动的提醒检查与更新检查照常进行；从托盘、菜单栏图标、老板键或再次启动打开窗口算一次显式重开。启动尚未完成时从托盘或再次启动打开，会在窗口就绪后显示；macOS 启动过程中自带的 `activate` 不算打开。Windows 开机时若有待安装的更新，仍先显示安装进度，装好的新版带窗口打开。
- `tests/login-item.test.ts` 覆盖任务管理器停用、写入回读不符、macOS 待批准或已在系统设置关闭、开发运行不登记与开机自启识别；`tests/lifecycle.test.ts` 覆盖后台驻留启动只报告一次冷启动、启动中 macOS `activate` 不显示窗口、显式打开为重开，以及启动期间的显式打开在就绪后显示窗口。生产构建在 Linux Electron（隔离数据目录）中以替换为内存登录项的临时构建走查了各设置状态、键盘操作与焦点、快速重复点击、浅深色与窄窗截图、写入不符通知、启动后立即再次启动显示窗口；200% 缩放只测量了开关未越出视口。
- Windows 原生验收（NSIS 安装包，断网的 Windows Sandbox，系统构建 26100）：当前用户静默安装后在设置中开启，Run 下登记 `"…\xidao.exe" --xidao-login-launch`；写入任务管理器的停用标记后开关显示为关，再在汐岛中开启即清除停用标记；沙盒真实重启并登录后，汐岛由开机项启动，桌面与任务栏没有窗口、只有托盘图标，点击托盘图标打开窗口；直接执行 Run 中登记的命令时没有可见窗口，再次启动后显示窗口；以 `--updated` 覆盖安装后登记保留；静默卸载后 Run 与 `StartupApproved\Run` 中的值均已删除。macOS 登录项、待批准提示与 `wasOpenedAtLogin` 尚未原生验证。

### 后台驻留与老板键

- 后台驻留时任务栏和 Dock 中都没有汐岛。Windows（及 Linux）从托盘图标打开：单击打开窗口，右键菜单为“打开汐岛”“退出汐岛”。macOS 菜单栏始终有一个单色模板图标（`resources/icons/tray-template.svg` 为源，导出 16px 与 32px PNG），任意点击弹出同样的菜单；进入后台驻留时窗口隐藏后执行 `app.hide()` 与 `app.dock.hide()`，菜单栏交还前一个应用、⌘Tab 不列出汐岛，重新显示窗口时 `app.dock.show()` 恢复 Dock 图标。开机后台驻留启动在创建窗口、加载页面之前就隐藏 Dock 图标；应用进程刚启动、代码尚未运行时系统显示的图标仍会短暂出现。从访达、启动台或聚焦搜索再次打开汐岛时经 `activate` 恢复窗口，菜单栏图标被刘海或其他图标挡住时也能找回。
- 主进程自己记录窗口是否由应用显示，而不读 `isVisible()`：macOS 上被其他窗口完全挡住的窗口 `isVisible()` 也为假，老板键会误判为已隐藏。应用菜单中的“隐藏汐岛”（⌘H）按已隐藏处理。
- 老板键是唯一的系统级快捷键（Electron `globalShortcut`），设置 `bossKeyEnabled`（默认关）与 `bossKey`（Electron 加速键，规范顺序 `Control+Alt+Shift+Command/Super+键`，默认 `Control+Alt+H`）只属于本机。窗口在屏幕上（含无焦点、在副屏、被遮挡）时按下进入后台驻留；后台驻留或最小化时按下显示并聚焦窗口，算一次显式重开（托盘、再次启动等其他入口恢复最小化窗口仍不算）。退出流程询问草稿时仍可隐藏，退出不取消；发送收尾期间按下与从托盘打开相同，取消自动退出。与“关闭窗口时”的设置互不影响，不额外静音系统通知。
- 组合键须以字母、数字或 F1–F12 结尾，并含 Ctrl、Alt、⌘ 或 Win 之一（只有 Shift 不行），也不能是汐岛自己使用的组合（标签、刷新、保存、搜索、缩放还原、编辑菜单，macOS 的 ⌘H／⌘Q／⌘M／⌥⌘H／⌃⌘F／⌥⇧⌘V，Windows 的 Alt+F4）。设置页录入时主进程暂时注销当前组合，并在窗口的 `before-input-event` 中拦下每次按键（Tab、Shift+Tab 照常移动焦点），经 `boss-key:input` 交给设置页判断：页面、菜单快捷键（⌘Q、⌘H 等）和 Alt+F4 都不会执行，不能用的组合就地说明原因。Esc、失焦、离开设置页或页面导航都会结束录入并重新登记。
- 系统拒绝登记（通常是其他程序已占用）时开关保持开启，设置行显示“未生效，组合键可能已被其他程序占用”；启动、每次设置变更、设置页显示及窗口回到前台时重试，不弹系统通知。Linux 没有老板键，设置中不显示。
- `tests/boss-key.test.ts` 覆盖录入规则、录入时窗口交出的按键（Tab 例外、⌘Q 与 Alt+F4 被拒）、显示、设置校验与登记（设置变更即登记、按下调用回调）／重试／录入暂停；`tests/lifecycle.test.ts` 覆盖切换、老板键恢复最小化窗口算显式重开而托盘恢复不算、退出询问中隐藏以及后台驻留启动期间按下。生产构建在 Linux Electron（隔离数据目录、外网阻断）中以放开平台限制、模拟某组合被拒的临时构建走查了设置的关／开／录入／拒绝说明／未生效／恢复默认、浅深色、窄窗与 CSS 两倍缩放；另以 `webContents.sendInputEvent` 经窗口输入管线送入 Ctrl+W、Ctrl+0、Esc，确认录入中这些按键只交给设置页（页面未收到 keydown、设置标签未关闭、显示冲突说明），Esc 结束录入。WSLg 下系统级按键未能触发，切换行为、⌘Q／Alt+F4 在原生系统上是否被拦下、Dock 隐藏与恢复、默认组合是否被占用及菜单栏图标外观均须在 Windows／macOS 原生验证。

### 启动公告

- 公告服务只读取固定 `https://nmb.ovear.info/nmb-notice.json`，专用传输无凭据来源、不跟随重定向，总超时 10 秒，压缩与解压响应各限 128 KiB。冷启动后台读取一次，窗口恢复不触发读取；设置中的主动重试共用在途请求。
- `enable` 必须为布尔值；仅 `true` 且安全解析后有可见正文才能自动展示。`date` 保留完整字符串或安全整数，不截成日期；抑制身份直接比较完整 `date` 与原始正文，同日期正文修订可再次提示。正文复用受限解析与展示，不执行 HTML，不加载外部图片；引用只在明确点击后定位，不因展示或悬停预取。
- 最近公告与抑制选择一起保存在现有 `settings` 表的独立 `announcements` 行，无 schema 变更；普通缓存清理和其他设置更新不覆盖该行。写入串行化，“不再提示”持久化成功后才关闭；失败可继续关闭本次提示，不伪报已保存。初始记录不可读时不覆盖未知选择，也不自动弹窗。
- main 原子发放一次自动展示资格，并检查原生窗口可见、未最小化且聚焦；renderer 还须等工作区与启动发送恢复检查完成，避开编辑器、其他模态、输入焦点和发送操作。迟到结果保留等待，不夺取现场。网络或协议失败保留本地副本供主动查看，不以旧副本自动弹窗。
- 聚焦验证覆盖真实临时 SQLite 重开、只读失败、清理保留、写入竞争、IPC 调用方与参数边界。Linux 实际 Electron 验证延迟响应与恢复编辑器、关闭／抑制／同日期修订、主动重试、键盘焦点、浅深色及窄窗 200% 缩放；这些证据不替代 Windows／macOS 原生验收。

### 第三方服务授权

- `thirdPartyConsent` 独立 settings 行保存告知版本及更新／搜索开关，无 schema 变更；统计仍以 `analytics` 行为唯一选择来源。缺失或非法记录按未告知处理，三个网络闸门均默认关闭，包括旧版已开启统计的安装。
- 首次弹窗复用设置页开关，三项默认关闭，拨动仅改变本地待保存选择，明确保存或全部拒绝后才结束；Esc、外部点击和关闭事件不能跳过。接收方、发送内容、风险与保留信息完整放在可滚动的说明区，底部操作不随长文滚走。在工作区恢复且前台无其他模态后显示，优先于公告；恢复的草稿先收起，不让编辑器挡住首次告知。退出时暂时收起，取消退出后继续询问。
- 保存授权成功才允许相应请求。全拒绝保存失败时，可明确继续使用，本次仍全部关闭，下次启动重新询问。撤回立即关闭闸门并取消可取消请求；撤回保存失败时明确提示本次关闭、下次启动可能恢复旧选择。授权修改串行化，迟到的开启不能覆盖后来的撤回。
- 已同意不重询；拒绝后主动进入联网搜索或手动检查更新只询问对应服务，拒绝不在原地循环弹出。恢复的搜索页不自动询问或提交；进入页同意只聚焦，提交／翻页等明确动作同意后才继续一次，离开页面取消待执行动作。统计拒绝后仅能从设置主动开启。
- 更新的定时检查、手动检查、下载及网络会话都核验授权；撤回停止调度并中止下载。已有本机安装包的本地安装操作不受网络授权影响。electron-updater 的更新元数据请求带 `x-user-staging-id`，值保存在用户目录 `.updaterId`，用于更新分组，不是统计服务的标识。
- 主进程对搜索请求、固定搜索站点及对应通用外链入口同样核验授权，服务分类统一处理域名末尾点和 GitHub 仓库路径大小写；普通无关外链保持原有行为。关闭保留已取得页，不消耗尚未使用的翻页标记，已发出后中止的标记不重放。论坛与本机功能不依赖这些授权。
- `tests/third-party-consent.test.ts`、统计／更新／搜索服务与 IPC 测试覆盖升级、持久化失败、并发撤回、在途取消和绕过入口；`tests/renderer/third-party-prompt.test.ts` 覆盖提示顺序与动作继续条件。生产构建已在 Linux Electron 隔离目录、回环受控网络下走查首次全拒绝与混合选择、搜索拒绝重入、同意后不重询且不自动提交、真实搜索提交、设置撤回、重启及浅深色／窄窗／200% 缩放；控制 IPC 失败响应另验证保存失败、拒绝后本次继续与快速重复输入锁定。等价服务外链在未授权时返回拒绝且未调用系统浏览器。不代替 Windows／macOS 更新安装和系统凭据原生验收。

### 使用统计客户端

- 接收服务来源在构建时由 `MAIN_VITE_XIDAO_ANALYTICS_ORIGIN` 固定，只接受不带路径的 HTTPS 来源，或仅用于隔离开发／验收的本机回环 HTTP。正式值写在随仓库提交的 `.env.production`，electron-vite 在 `npm run build` 与两个 dist 命令中读取它，所以本地打包与 CI 构建取值一致；开发模式不读取该文件。构建时环境里已有的同名变量优先：隔离验收构建可指向回环服务，设为空值则关闭此功能。未设置、来源不合格、Linux 或数据库不可写时统计不可用、不发送；首次告知及设置仍说明原因。renderer 不能指定地址，也拿不到凭证。
- 同意状态为未选择／关闭／开启，与统计标识、受保护凭证和最近成功上报的统计日一起保存在 `settings` 表的独立 `analytics` 行，无 schema 变更；旧数据库没有该行即为未选择（关闭），其他设置更新与缓存清理不改动它。凭证经 `safeStorage`（Windows DPAPI、macOS 钥匙串）加密后以 base64 存放，系统保护不可用时拒绝开启、也不登记。
- 只有第三方告知已完成且“开启”持久化成功后才登记与上报；登记得到的标识与凭证先落盘再发第一次活跃上报。“关闭”先停止本轮调度并中止在途请求，再保存；保存失败时本次运行保持关闭，下次启动按实际存储状态处理。每轮统计有代次，已停止轮次的迟到响应不写记录、不改调度。
- 前台由主进程判定：窗口可见、未最小化、聚焦，且未锁屏（`lock-screen`／`unlock-screen` 与 `getSystemIdleState`）、未休眠。窗口的 show／restore／focus、解锁与唤醒触发检查，另有最长 15 分钟、并在北京时间零点后 1 秒到期的复查定时器覆盖前台跨日。服务端返回的 `statDay` 记为已上报，同一统计日不再请求。
- 请求节奏：单次在途、10 秒超时、两次自动尝试至少间隔 60 秒（单调时钟，不受系统时间调整影响）；无响应或 5xx 依次退避 5 分钟／30 分钟／2 小时，`429` 遵守 `Retry-After`（至少 60 秒、最多 24 小时），`capacity_exhausted` 等 2 小时，其他 4xx 本次运行不再自动尝试；每个本地统计日每次运行最多 6 个自动请求（登记与上报合计）。登记响应返回、或本次运行首次解密已存凭证之后，都重新检查前台与剩余预算，再决定是否上报；否则只保留身份，等下一个合格的前台时刻。服务端统计日与本机不一致时 30 分钟后在预算内复查。不建立离线队列，不补报。`403 invalid_credentials` 表示服务端已无此身份（31 个统计日没有上报而过期）：仅在仍开启时丢弃旧身份并重新登记。
- 关闭只停止以后的上报，本机保留标识与凭证，再次开启沿用；服务端的关联记录只按保留期过期。
- 聚焦测试 `tests/analytics-client.test.ts` 用真实临时 SQLite、本机受控 HTTP 与受控时钟覆盖：旧数据库默认未选择、同意前零请求、受保护凭证先落盘、同日去重与重启、前台跨零点与后台不计、登记或凭证解密期间离开前台不上报、保存失败与关闭失败、关闭中止在途请求且迟到响应无效、退避与 `Retry-After` 与日预算、身份失效后重新登记；另以实际服务进程验证上报、看板计数、关闭后不再上报且当天计数保留。首次提示与公告的先后由统一第三方告知测试覆盖。
- 该测试等待请求到达受控服务或中止被服务端察觉时，用带时间上限的 `expect.poll`，不按事件循环轮数计：本机回环连接与请求解析的延迟是墙上时间，并发跑全套时可从约 1 ms 增至数毫秒，而空转的轮次很快耗尽，测试会在服务仍正常推进时误判失败。等待服务回答用 `settle()` 直接等在途请求结束。
- 以下两项是统一第三方告知接入前的历史原生验证，其 Esc 操作属于已替换的旧统计询问，不证明现行首次弹窗已完成原生验收。
- 原生实际客户端验证（从源码 `npm run build` 的未打包应用，隔离数据目录与独立的系统凭据项，`MAIN_VITE_XIDAO_ANALYTICS_ORIGIN` 指向本机隔离的统计服务进程，服务与客户端共用同一偏移后的墙上时钟以演练跨日，论坛与其他出站请求被拒绝）。Windows 11 x64 与 Apple Silicon macOS 各跑同一组场景并全部通过：首次询问的焦点、Tab、480 px 与 200% 缩放、Esc 保存关闭后才出现公告；设置开启只发一次登记与一次上报，请求体为协议白名单字段、平台分别为 `windows`／`macos`，凭证以 `safeStorage` 的 `v10` 密文保存（Windows 密钥由 DPAPI 保护，macOS 密钥在钥匙串）且数据库中无明文；看板计数；焦点／隐藏／最小化风暴无额外请求；关闭跨重启保持；同日去重；前台跨北京时间零点上报一次；最小化跨零点不计、恢复后上报一次。首次询问与设置页的现行界面尚未做原生走查。锁屏未做原生演练，只由 `lock-screen`／`getSystemIdleState` 接入与受控时钟测试覆盖；Intel Mac 未单独实测，统计逻辑与 Apple Silicon 相同，平台差异只在系统凭据与窗口事件。这些都是隔离的本机演练，不代表正式接收来源或部署已验收。
- 正式接收来源的组合验证：Windows 11 x64 上从 `.env.production` 构建、未覆盖来源的未打包应用（隔离数据目录与独立系统凭据项，公告走受控源，论坛等其他出站被拒绝），对已部署的服务串行完成首次 Esc 关闭零统计请求、设置开启后一次登记与一次上报、真实浏览器看板（HTTPS＋Basic 认证）计入该实例与 `windows` 分桶、焦点风暴与关闭后无请求、关闭跨重启保持且不撤回已计数的当天、本机库中无明文凭证。跨日、锁屏与 macOS 差异沿用上一条的隔离演练；服务器侧的部署、日志与保留核对见 [使用统计服务](analytics-service.md#正式部署)。

### 联网搜索与串号定位

- 联网搜索只使用 nmb-search。论坛接口（`/api/ref` 等）不提供发言所属串，nmb-search 也不收录回复号，所以没有按串号反查所属串的来源。
- 每个搜索历史条目保留自己的查询链、结果页和请求代次。返回只恢复现场；只有提交、翻页和主动重试才能联网。旧响应只能落在原条目，旧查询不得覆盖新查询。失败保留已取得结果，不预取或自动重试。
- 请求固定到 `https://nmb-search.166666666.xyz/api/v1/web`，UA 由 `app.getVersion()` 生成 `Xidao/<version>`。下一页只发送一次 `npt` 令牌：取消或响应丢失不重放，失败的下一页不提供重试，只能重新搜索；已取页保留。
- 传输限定来源、拒绝重定向、限制压缩／解压体积和总等待时间，没有可携带凭据的来源。主进程不接收 renderer 给出的服务 URL 或身份字段，“打开搜索网站”只打开固定站点。服务的 `Retry-After` 只形成运行期截止时间，不臆测每日额度或请求间隔；冷却期间的新搜索不发请求，也不替换当前结果链；关闭或重开搜索页不解除仍有效的截止时间。
- 普通空结果、服务状态消息、HTTP 错误、验证要求和限流分别处理。响应文本只作为去除控制字符的有界纯文本；结果链接只保留不含账号信息的 http(s) 地址，只有核验过的论坛主机与路径形式才在汐岛内定位打开。
- 旧版本保存的设置项 `onlineSearchChannel` 不再读取，留在 settings 表中也不影响其他设置的读写，无须 schema 变更。
- 显式串号输入与正文引用共用 1–20 位正十进制字符串校验；论坛链接的 `r`／`page` 只是待验证线索。定位依次依据本机已见记录、论坛链接线索、主帖串号，最后是引用所在的串；不逐页遍历整串猜页码。只有既有阅读定位核实成功才能提交目标导航，只知所属串时保留明确“打开原串”路径。失败不修改历史或创建空标签。
- 串内查找：`quotes.locate` 可带可选的 `context: { threadId, fromPostId }`（引用所在的串与所在发言），主进程按串号格式运行时校验，非法值走非法请求路径。界面只在明确定位（点击、Enter、在新标签页打开及失败后的“重试”）时传入：串阅读器正文中的引用与选中编号取当前串和所在发言，引用卡中的引用取卡片发言在本机已知的所属串；所属串未知的卡片、按串号打开、公告、搜索结果、发送记录与列表说明都不传，悬停与 Space 预览不会定位。本机记录和链接线索都定位不到时，先读 1 次该编号的第 1 页按主串检查；编号不大于所在串主串号时到此为止。否则在所在串的全部模式（`all`）中查找：同串回复编号随页码递增，引用只指向更早的发言，候选页上界取本机记录中 `fromPostId` 所在页（没有时按回复数算末页），再用本机已存的页按编号收窄，不为它们联网；先读上界页（引用所在页的前一页），再取区间中间页比较编号，直到命中或缩成空区间。网络读取次数最多为 1（主串检查）＋1（前邻页）＋⌈log₂(候选页数)⌉，读到的页照常存入缓存，之后按本机记录的既有路径核实。某页的编号范围覆盖目标却不含它（已删除或属于别的串）、区间缩空、目标只可能在无饼干第 100 页上限之后（不把重复的第 100 页当作请求页）、或没有任何回复数无法界定页数时，结果为 `unknown-thread`；读取失败为 `failed`，“重试”重新查找；取消后不再发出后续读取。
- 正文 `No.` 使用带 `readingOnly` 标记的安全 `quoteRef` 节点；提醒引擎只消费原有明确引用，便利阅读识别不扩大后台引用请求。裸数字保持文本，正文、引用卡和版规／说明共用完整有效选区的动作校验。卡片内选区替换预览时沿用原触发点或外层选区，不保留被替换正文的失效 Range；失败不提交导航，关闭后归还可恢复的来源焦点。
- 防剧透：揭开后单击该段文字（不含其中的链接与引用、也不含结束一次选取的点击）重新遮住；键盘揭开后焦点留在该段上，Enter／Space 再次遮住。遮住与揭开都即时切换，只有遮罩的悬停色有过渡；揭开后的文字不加底色，不新增文字与底色的对比组合。仍只在本次渲染内有效，不存储。
- 收藏版块的左侧栏缩写：独立设置 `boardMarks` 按版块键保存用户自定的缩写（1–2 个用户可见字符，不含空白、控制字符与零宽、双向控制等不可见格式字符；组合 emoji 的连接符保留），缺省时按原规则自动生成；不放进 `boards`，早于此功能的版本仍能完整读取收藏、隐藏、排序与折叠，无 schema 变更。可在收藏按钮的右键菜单（或 ContextMenu 键／Shift+F10）“自定义缩写…”与“设置 › 版块管理”的收藏行里修改，输入即保存，留空恢复自动缩写。菜单与编辑框挂在导航元素内、以顶层 popover 显示，窄窗导航浮层中操作它们不会关闭浮层。

### 主题列表

- 设置 › 外观的“主题”是单选列表：内置的“汐岛”固定在第一，其后是自定义主题，按加入的先后排列。选中即使用并保存，不经过“保存”；方向键在列表中移动即切换。“新建主题”从“汐岛”的内置色板、透明度与圆角生成名为“我的主题”的主题，加到末尾并使用，编辑器随之展开、焦点在名称。编辑器（默认折叠）只编辑正在使用的自定义主题，正在使用“汐岛”时不显示；有未保存的修改时成功切换主题（包括选“汐岛”）会放弃这些修改并清除预览，切换未能保存则保持原状。
- 行菜单：每行行尾的“⋯”按钮与右键该行打开同一个菜单（`src/renderer/src/components/ContextMenu.tsx`，沿用应用内菜单的方向键、Enter、Esc 与关闭后焦点回到触发处）；焦点在某行的单选钮上时 ContextMenu 键或 Shift+F10 也打开它，Esc 后焦点回到该单选钮。自定义主题的菜单为“复制”“导出…”和危险色的“删除”，“汐岛”只有“复制”。
- 复制：内容与原主题相同，名称为“原名 副本”；复制“汐岛”等于新建，只是名称为“汐岛 副本”。副本加到末尾并使用，编辑器展开、焦点在名称。重名时在“副本”之后加序号（“青瓷 副本 2”），超过 40 个字符时只截短原名部分。
- 删除：点击即执行，不确认。删除正在使用的主题后回到“汐岛”；删除当前主题时，若还有其他自定义主题，后一个（没有则前一个）成为当前主题但不启用。删除后焦点落到列表中的下一行，没有则上一行（“汐岛”总在第一行），都没有时落到“新建主题”。底部通知“主题已删除”（垃圾桶图标，下一行是主题名称）附“撤销”与关闭，显示时长、暂停条件与关闭方式与“草稿已删除”相同（`UNDO_WINDOW`）。通知在应用层（`useThemeListOperations`），关闭设置标签后仍可撤销。
- 撤销：主题回到删除时在完整列表中的位置（列表变短时放到末尾）；删除前正在使用的话同时切回使用，否则使用状态不变。名称在此期间已被占用的按自动命名规则加序号；列表已满 50 个时撤销失败，通知保留并写“没能撤销：已有 50 个自定义主题”，设置未能保存时写“没能撤销：设置未保存”。只有最近一次删除可以撤销，再次删除时上一条通知结束。
- 存储（[ADR 0006](adr/0006-current-custom-theme-stays-in-legacy-setting.md)）：当前自定义主题（正在使用的，或切回“汐岛”前最后使用的那个）仍在 `customTheme`，是否使用仍由 `customThemeEnabled` 表示；新设置键 `customThemeList` 为 `{ others, currentIndex }`：`others` 是其余主题的有序数组，`currentIndex` 是当前主题在完整列表中的位置。完整列表 = 把 `customTheme` 按 `currentIndex` 插回 `others`。主题对象不增加字段，无 schema 变更。
- 规则只在 `src/shared/themeList.ts` 实现：设置页的操作（选“汐岛”、选自定义主题、新建、复制、删除、撤销删除、保存修改）、主题文件的导入与按名称导出（`importTheme`、`exportedTheme`）和设置校验都调用它。每个操作得到一个设置补丁或拒绝原因，作为一次设置更新写入；切换是一次交换：原当前主题回到 `others` 中它的位置，被选中的进入 `customTheme`，列表顺序不变。`deleteTheme` 另外返回被删主题、它的位置与是否在用，`restoreTheme` 据此放回。renderer 的列表操作与撤销经同一个队列依次执行，每个操作基于上一个保存后的设置计算。
- 不变量（设置写入违反任一条即整体拒绝，原设置保持）：没有当前主题时 `others` 为空；`currentIndex` 在 0 到 `others` 长度之间；自定义主题总数不超过 50；名称去掉首尾空白后在全部自定义主题中唯一，且不能是“汐岛”。在编辑器里把名称改成已有名称或“汐岛”时，名称旁显示“已有同名主题”，不预览、不能保存。已有 50 个时“新建主题”“导入主题…”与各行菜单的“复制”为 `aria-disabled`（仍可聚焦），按钮旁与“复制”的提示写“已有 50 个自定义主题，删除一个后才能再添加”；删除一个后恢复可用。
- 自动命名遇到重名时在末尾加空格和从 2 起最小的未占用序号（“我的主题 2”）；加上序号超过 40 个字符时截短原名部分。
- 主题文件：格式仍为 `xidao-theme` v2，导入接受 v1／v2，解析规则不变（`src/shared/theme.ts`）：字体、字号、阅读宽度仍是必填字段并照常校验，但导入时不采用，本机的阅读设置保持不变；导出时照常写入当前的阅读参数。信任边界不变：路径只来自 main 弹出的系统对话框，renderer 不提供也拿不到路径；文件至多 64 KB、严格 UTF-8，逐字段校验。
  - 导入（“导入主题…”）：文件里的主题加到列表末尾并成为正在使用的主题，不覆盖任何已有主题；与已有主题或“汐岛”同名时按上面的规则加序号，结果行显示实际采用的名称（“已导入“青瓷 2””）。编辑器保持原来的展开状态，不自动展开；有未保存的修改时与切换主题一样放弃这些修改。已有 50 个时按钮为 `aria-disabled` 并显示上限说明；main 在写入前同样检查，列表已满时结果为 `{ status: 'failed', reason: 'full' }`，设置不变。
  - 导出：自定义主题行菜单的“导出…”导出那一个主题，不必先切换过去；“汐岛”不能导出，列表下方没有单独的导出按钮。renderer 只传 `{ name }`（`window.xidao.theme.export`）；IPC 层拒绝非对象、多余字段、非字符串和超过名称长度上限（40 个字符）的名称，走非法 IPC 参数的错误路径；main 确认它是现有的自定义主题后才弹出保存对话框，否则返回 `{ status: 'failed', reason: 'not-found' }` 且不弹框、不写文件。默认文件名取主题名称，`\ / : * ? " < > |` 替换为 `_`。对话框打开期间主题被改名或删除时同样返回 `not-found`、不写文件；写入失败为 `reason: 'write'`。
  - 旧版本导入新版本导出的文件时仍会按旧行为改掉自己的阅读字体、字号和宽度。
- 读取已存设置时逐项回退，不改写已存的行：`customThemeList` 缺失或不可读按没有其余主题；`others` 中无效的主题单独丢弃，位置随之前移；与当前主题、更靠前的主题或“汐岛”重名的按上面的规则加序号；超过 50 个时丢弃末尾的；没有当前主题而 `others` 非空时，第一个提为当前主题且不启用；位置越界时收到合法范围。
- 旧版本兼容：只认识单个主题的版本照常读写 `customTheme` 与 `customThemeEnabled`，不读写也不删除 `customThemeList`。升级后原有的单个自定义主题就是当前主题，列表里只有它，使用状态不变。装回旧版本时它显示当前主题；在旧版本里修改或导入主题只改写 `customTheme`，回到新版本后当前主题就是改写后的内容，其余主题与顺序不变（旧版本把它改成与其余主题同名时，读取时给其余那个加序号）。
- 个人数据导出：`customThemeList` 与 `customTheme` 同归“随文件覆盖”。

## 数据库迁移

- SQLite schema v8 按实际表结构归并早期订阅、同步计划、草稿／发布、保留内容与工作区；v9 追加提醒，v10 追加搜索派生表、FTS5 trigram、事务投影与逻辑字节核算；v11 给饼干加入列表顺序，并把原“浏览饼干”用途并入顺序（原浏览饼干排到首位）。迁移单个事务完成并保留个人记录。已知早期 v2 且已有 `credentials` 表的数据库无法升级；早期独立搜索开发分支的同号 v8 库缺少这条历史所需的发布／工作区表，也会拒绝升级并保持原文件不变。不把版本号相同当成结构相同。
- SQLite schema v12 追加独立账号会话表，只接收非空 BLOB 密文与到期时间；账号会话不参与浏览／发言／网页订阅身份选择。v13 追加本机屏蔽表（串号或饼干标识），只在本机使用，不发送到论坛。v14 在同一迁移事务中删除串收藏、逐条已读记录与关注起点三张表，不迁移其中的数据；阅读位置、访问记录、提醒及其补查所用的页观察与末尾观察保留。v15 给饼干加入可空的饼干 ID 列（升级前的饼干为空），并删除“我的发言”记录表；发送尝试、结果状态与确认到的编号保留在发送记录中。
- v16 把提醒改为回复数基线：保留每条提醒规则、是否开启及其代次（原起点时间作为最近开启时间），删除旧的起点与水位、补查覆盖、检查轮次、逐事件提醒、通知登记和末尾观察，不做转换；新增按串、按提醒种类保存基线、已核对编号与计数的表，以及上次检查时间。升级后的第一次检查只为所有开启的规则重建基线、不计数。迁移在单个事务中完成，失败时原库保持不变；换回旧版本时不承诺能读取新的提醒数据。
- v17 给提醒检查器追加退避间隔、限流事件、已通知与已确认状态，保留 v16 的规则、基线与计数；迁移失败时在事务内回滚，不清空提醒。运行中写库失败时，当前进程仍保守延长限流间隔，确认或解除通知状态须写入成功后才生效；尚未写入的新退避不能保证在重启后保留。
- v18 删除草稿表的 E-mail 列，草稿的目标、饼干、标题、名称、正文、水印与附图保留；已有发送记录中保存的原始载荷不改写，其中的 E-mail 不再显示或使用。迁移在单个事务中完成，失败时原库保持不变；不承诺旧版本能读取升级后的数据库。
- v19 给发送尝试加入发送时的饼干 ID，并允许失败原因记为“可能已发出、核对未找到”；只有发送中与结果不明的尝试锁定来源草稿。已有尝试的饼干 ID 取升级时该饼干（本地编号不复用）已知的饼干 ID。SQLite 不能就地修改约束，因此在同一迁移事务中重建该表，保留全部尝试、编号与不复用的编号计数。迁移失败时回滚，原库保持不变。

- 迁移链不得截断或合并到导出功能首个发布版本的结构版本之前：任一已发布版本导出的文件都必须能从它的结构版本迁移到当前结构（ADR 0005）。

- 首版导出文件样本：`tests/fixtures/personal-data-v29.xidao`（不加密）与 `tests/fixtures/personal-data-v29-encrypted.xidao`（带饼干与 App UUID，口令写在 `tests/personal-data-samples.test.ts`）是导出功能首个发布格式的文件，用合成数据导出，覆盖每个随文件覆盖、目标机保留并追加与秘密的类别。它们代表用户手里已有的文件，不得重新生成或替换。每个新迁移都须让 `tests/personal-data-samples.test.ts` 通过：两个样本在暂存中迁移到当前结构后导入新安装，各类内容与原来一致；迁移有意改变某类数据的形状时，只改测试读取它的方式。

### 升级前备份

- 已有数据库（结构版本 1 及以上）需要迁移时，汐岛在任何迁移或其他写入之前，先在用户数据目录下的 `backups/pre-upgrade/` 保存升级前备份：迁移前数据库的一致快照 `xidao.sqlite`（包含 WAL 中已提交但还没写回主文件的内容，保存为单个文件）、`draft-images/` 中全部受管附图副本（不含符号链接和中断留下的临时文件），以及清单 `manifest.json`。清单记录格式版本 `format`、备份的结构版本 `schemaVersion`、执行这次升级的汐岛版本 `appVersion`、备份完成时间 `completedAt`，以及各附图副本的名称与大小 `draftImages`。图片缓存 `images/` 不备份，缺失的缓存图片之后会重新下载。新安装和无需迁移的启动不备份。
- 只保留最近一份。快照通过只读连接取得，新备份先完整写到 `backups/pre-upgrade.partial/` 并校验：清单完整，附图副本齐全且大小一致，数据库副本的结构版本与清单一致，并通过 SQLite 完整性检查。校验通过后才替换上一份。替换中断时，上一份保留在 `backups/pre-upgrade.replaced/`，下次备份或读取备份时放回原位；任何失败都不会留下可被当作备份的半份内容。备份所需时间随数据库大小增加，没有单独的进度界面。
- 备份失败（例如磁盘空间不足、目录不可写）时不迁移，原数据库文件逐字节不变。本次运行的存储状态为不可用，不读也不写数据库；退出时与其他不可用状态一样直接退出，不保存工作区，也不安装更新。标签栏下方的提示条说明升级前的备份没有成功、数据还未升级，并提供两个操作：
  - “重新启动重试”：重启后重新备份并升级。
  - “不备份升级…”：确认后在用户数据目录记下一次性选择 `upgrade-without-backup.json`，然后重启。下次启动时，数据库仍是同一结构版本才跳过备份直接迁移。无论是否迁移、迁移是否成功，这次选择都在该次启动时清除，不影响以后的升级。数据会保留并升级，但之后改用旧版本时无法回到升级前的状态。
- 迁移本身失败的处理不变：事务回滚，原库保持不变，存储不可用。
- 两个操作都经正常退出流程结束本次运行，再启动新进程。新进程先等待旧进程结束（最多 60 秒），然后才取得单实例锁并打开数据库，因此不会与旧进程同时打开数据库，也不会因单实例锁被旧进程占用而直接退出。
- 验证范围：存储测试以隔离的临时 SQLite 和合成的新旧迁移列表覆盖 WAL 内容进入备份、附图副本与清单、新安装和无需迁移时不备份、备份失败时原库逐字节不变且上一份备份完整、不备份升级只生效一次（迁移失败时同样清除）。Linux 上以生产构建、隔离用户数据目录和断网环境实际走查了升级备份、备份目录不可写时的提示条与对话框、两种重启及其后的升级。Windows 11 x64（NSIS 安装包在断网的 Windows Sandbox 中覆盖安装，以及免安装目录 `win-unpacked`）与 macOS arm64（DMG 中的应用）上以隔离用户数据目录原生验证了升级时生成备份（含只读的附图副本）；备份失败后的两种重启只在 Linux 上走查。Intel Mac 未原生验证。

### 降级与恢复升级前备份

- 较旧版本打开较新版本写入的数据时，标签栏下方的提示条说明数据来自更新版本、这里只能查看，改动不会保存；“了解更多”在浏览器中打开本节。误开了旧版时直接改用新版即可：只读期间数据库文件不被写入，新版照常打开，不会重新备份。
- 如果 `backups/pre-upgrade/` 中的升级前备份可以恢复（清单有效，备份的结构版本不高于当前版本支持的版本，数据库副本通过完整性检查，附图副本齐全），提示条另有“恢复升级前备份…”。打开确认框之前，汐岛以只读方式检查当前数据的三张秘密表能否读懂；确认框写明备份时间、备份来自哪个版本（即当时升级到的版本），按类别列出会丢失的改动（备份之后的草稿与发送记录、导入的饼干、阅读位置与访问记录、设置、屏蔽、饼干颜色、离线副本、提醒），不逐条比较。
- 确认后，在本次运行中把备份复制到 `backups/restore-staging/`，在副本上去掉升级后已删除的秘密，当前数据只读不改，也不解密任何秘密：
  - 饼干凭据与 App UUID 只保留本地编号（`id`）仍存在于当前数据中的；当前数据没有官网账号会话时，去掉备份中的会话。因此升级后移除的饼干、退出的官网登录不会因恢复回来，升级后新导入的饼干也不在恢复结果中。
  - 当前数据的秘密表读不懂时（以后的迁移改了表名或键列），三张表的全部行都去掉，确认框提示饼干和官网登录需要重新导入。
  - 被去掉的饼干按正常移除处理：草稿、默认发言饼干与各串记住的发言饼干仍引用它，显示为“已移除”。被去掉的 App UUID 如果正是订阅配置使用的，配置回到“未配置”并换用新的配置代次；以前的观察、操作与同步计划留作历史，不会在新代次下继续执行，按现有流程重新配置即可。
- 准备完成后写入恢复日志 `backups/restore-journal.json`，经正常退出流程重新启动；准备失败时确认框内说明失败，数据和文件都不改动。下次启动在打开数据库之前按日志执行：先把当前的 `xidao.sqlite`（连同 `-wal`、`-shm`、`-journal`）和 `draft-images/` 移到 `backups/before-restore/`（先在 `backups/before-restore.partial/` 汇齐，再替换上一份降级前数据），再把恢复副本移到原位，最后清除日志。每一步都可重复执行；中途被中断时，下次启动继续完成，恢复副本缺失或不完整时放弃恢复、把当前数据放回原位照常打开，提示条说明“恢复没有完成，数据没有改动”。日志无法读取或文件系统拒绝某一步时，本次运行不打开数据库（存储不可用），下次启动再继续。
- 恢复日志是通用换库日志的一种（`src/main/storage/swap-journal.ts`；另一种是导入，见“导入个人数据”），日志记录操作种类与阶段，同一时刻最多一个待执行的换库：已有待执行的换库（或日志无法读取）时不开始新的，已有日志和暂存数据原样保留，确认框按准备失败说明。日志沿用包含恢复功能的各版本都会检查的路径；恢复日志保持这些版本能读的格式（`format` 1，没有种类字段的旧日志按恢复处理），以后新增的换库种类使用它们拒绝的格式（导入为 `format` 2），较旧版本因此不打开数据库，而不是在换库中途打开。
- 恢复后的数据库结构版本低于当前版本时，照常先做升级前备份再迁移。图片缓存不在备份中：恢复库中没有记录的缓存文件在启动清理时删除，缺失的缓存图片之后重新下载。恢复后再换回较新版本时，较新版本会把恢复后的数据（含旧版本此后的写入）重新备份，然后升级。
- 降级前数据不会自动删除，下次恢复时才被覆盖。手动换回降级前数据：
  1. 完全退出汐岛（托盘菜单“退出汐岛”）。
  2. 在用户数据目录中，把当前的 `xidao.sqlite`、`xidao.sqlite-wal`、`xidao.sqlite-shm`、`xidao.sqlite-journal`（存在的）和 `draft-images/` 移到别处保存。
  3. 把 `backups/before-restore/` 中的这些文件和 `draft-images/` 移回用户数据目录。
  4. 用较新版本的汐岛打开。用旧版本打开时，它仍是只读。
- 本功能之前的版本（v1.0.0、v1.1.0 等）没有恢复入口，打开较新的数据时只读。升级到包含本功能的版本时已经自动产生升级前备份，可以手动恢复：
  1. 完全退出汐岛，记下 `backups/pre-upgrade/manifest.json` 中的 `schemaVersion`。旧版本支持的结构版本：v1.0.0 为 21，v1.1.0 为 23；`schemaVersion` 高于要安装的旧版本时，这份备份它也只能只读。
  2. 按上一条第 2 步把当前数据移到别处保存。
  3. 把 `backups/pre-upgrade/xidao.sqlite` 和 `backups/pre-upgrade/draft-images/` 复制到用户数据目录。
  4. 用旧版本打开。手动恢复不会过滤秘密：升级后移除的饼干和退出的官网登录会回来，请在设置中再次移除或退出。
  - 早于本功能的升级没有自动备份；没有自己备份过用户数据目录时，旧版本只能只读查看较新的数据。
- 验证范围：存储测试以隔离的临时 SQLite 和合成的新旧迁移列表覆盖恢复入口的判定（备份比程序新、清单损坏、完整性检查失败、附图缺失）、秘密过滤（读得懂与读不懂两种情况，含订阅配置代次与历史记录）、恢复日志每一步之后中断再启动、只读期间文件不变与恢复后再升级；IPC 测试覆盖调用方、参数与返回内容。Linux 上以生产构建、隔离用户数据目录和断网环境实际走查了只读提示条、确认框与恢复后的重启。Windows 11 x64 与 macOS arm64（DMG 中的应用）上以隔离用户数据目录原生验证了完整往返：较新版本升级并备份，旧版本只读打开后恢复并自动重启（旧进程退出后才移动文件，始终只有一个主进程），数据回到升级前、升级后移除的饼干没有回来、`backups/before-restore/` 保存较新数据，再用较新版本打开时重新备份并升级；只读的附图副本也能正常备份和恢复。Windows 上这一往返分别用免安装目录 `win-unpacked` 和 NSIS 安装包走过：后者在断网的 Windows Sandbox 中依次覆盖安装较旧、较新、较旧（安装器接受降级）、较新版本，每次只有一条卸载项且版本随之更新。Intel Mac 未原生验证。

## 导出与导入个人数据

用户可以在设置 › 存储与缓存把个人数据导出成一个 `.xidao` 文件，在另一台电脑或重装后的汐岛导入。导出文件是本机数据库裁剪后的快照，加上草稿附图和（可选的）离线副本原图；导入整体替换个人记录与设置，本机找不回来的数据保留下来（[ADR 0005](adr/0005-export-file-is-trimmed-database-snapshot.md)）。每类数据怎么处理只由数据归类（`src/main/storage/classification.ts`，规则见“数据库迁移”）决定，导出裁剪与导入合并不另列名单：

| 归类 | 包括 | 导出 | 导入时本机 |
| --- | --- | --- | --- |
| 随文件覆盖 | 浏览历史与阅读位置、发送记录、屏蔽、饼干颜色、提醒、默认发言饼干与网页同步对象、各串记住的发言饼干、订阅配置与记录、工作区、X 岛公告状态、下一行以外的设置 | 带上 | 换成文件中的 |
| 目标机保留 | 关闭窗口时的操作、开机与老板键、列表宽度、更新相关设置、普通缓存上限、使用统计实例、第三方授权、官网账号会话 | 不带 | 保持本机的 |
| 目标机保留并追加 | 离线副本（含页、发言与原图）、草稿与草稿附图 | 带上（离线副本可不勾选） | 本机的保留，与文件中的合并 |
| 秘密 | 饼干凭据、App UUID | 只在勾选时以导出口令加密带上 | 文件中的用本机系统保护重新加密，本机的保留 |
| 不导出 | 普通缓存、搜索索引、图片持有关系、提醒检查器状态 | 不带 | 由本机重建或回到初始状态 |

### 导出个人数据

- 入口在设置 › 存储与缓存的“个人数据”一行（“导出个人数据…”，旁边是“导入个人数据…”，见下一节）。只有存储可写时可用；数据库只读时两个按钮都不可用，旁边一句“当前数据库只读，不能导出或导入”，存储不可用时为“存储不可用，不能导出或导入”。对话框列出文件包含的内容；有离线副本时多一项“离线副本（N 个串，约 X）”，默认勾选；另有“饼干与 App UUID”，默认不勾选。不勾选时文件不加密，对话框写明这一点；勾选后要输入两次导出口令（见下文“加密与导出口令”），两次不一致时在第二个框旁说明；在任一框输入过之后第一个框为空时，在第一个框旁说明“口令不能为空”（刚勾选、尚未输入时不说明），补全后消失；口令为空或不一致时“导出…”不可用。
- 在本机数据库的一致快照副本上按数据归类裁剪（`src/main/storage/export-snapshot.ts`），本机数据库只读访问、不被改动：
  - 随文件覆盖的表和设置行原样保留。
  - 目标机保留的表与设置行清空。不带饼干与 App UUID 时秘密表（饼干凭据、App UUID）也清空，不带任何密文；带上时这两张表的行保留，密文换成为文件封装的值（见下文），文件里没有源机系统保护的密文。清单都记录饼干凭据编号序列的上界。
  - 由目标机重建的数据回到初始状态：搜索索引清空并标为未建立，图片持有关系、阅读持有者、提醒检查器状态清空，内容时钟与各行的使用顺序归零。
  - 不勾选离线副本时，先删掉离线副本及其页、发言与原图关系，再裁剪普通缓存，只被它们保护的内容随之不导出。
  - 普通缓存用“清理普通缓存”的同一规则（`evictContentBatch`）清理：访问记录保护的主帖文字与回复数、草稿目标串的内容、离线副本的发言与原图保留，其余缓存、缩略图和未被离线副本引用的图片都不导出。发言与串的归属记录（`post_threads`）照常保留，与清理缓存后的状态一致。
  - 裁剪后检查外键与 SQLite 完整性，再 `VACUUM`，被删除的内容不会留在空闲页里。
- 快照与裁剪在独立的 worker 线程里用只读连接完成（与升级前备份相同的 `VACUUM INTO`，包含 WAL 中已提交的内容），汐岛照常可用；快照时刻之后的改动不进入文件。快照后立即打开草稿附图与离线原图的文件句柄：之后再被删除也照样读出。快照记录的离线原图文件已经不在时，该图在文件里的离线副本状态记为“本地没有保存这张图片”（与原图保存失败的显示相同），图片记录不带入；草稿附图文件已经不在时，草稿与发送记录不带附图。
- 流程：有发言正在发送时拒绝（结果未知的发送不算），保存对话框在 main 中显示（默认文件名 `汐岛个人数据-<YYYY-MM-DD>.xidao`，按本机日期；不注册文件关联），估算总量（数据库文件与 WAL、草稿附图、勾选时的离线副本）并检查目标所在磁盘的可用空间（还要容纳写出期间的数据库快照），不足时说明还差多少、不开始。写出到目标目录中以 `.` 开头、`.part` 结尾的临时文件，完成并刷盘后才改名为目标文件；进度是已写字节／文件总字节。取消、失败（包括写入中磁盘写满）或退出汐岛时，先删除临时文件与快照副本再报告结果，不会留下残缺的目标文件。退出流程在停止后台工作时取消正在进行的导出并等待清理完成。进程被强制结束时，目标目录里可能留下以 `.` 开头的 `.part` 临时文件，可以直接删除。
- 进行中可以关闭对话框，进度留在存储与缓存；完成后显示文件名并提供“在文件夹中显示”。界面只拿到文件名，拿不到任何路径或秘密。界面向 main 读取的预估同时带回当时正在进行的导出（让错过它的窗口接上进度）：main 在回复时才读取，导出先清除进行中状态再报告结果；界面已听到结果之后才收到的、更早发出的预估不再改动导出状态，所以结束的导出不会被迟到的预估重新显示为进行中。具名操作 `personal-data:export-estimate`、`start-export`（参数恰好是 `includeOffline` 布尔值与 `passphrase`：`null` 表示不带秘密，否则为非空字符串，不限长度）、`cancel-export`、`reveal-export` 与进度事件 `personal-data:export-progress` 经主窗口主框架调用方校验与运行时参数校验。导出时本机有饼干或 App UUID 无法解密（包括系统保护不可用）时，导出失败并说明“导出失败：本机的饼干或 App UUID 无法解密”，不留下文件。
- 文件格式（`src/main/personal-data/container.ts`）：8 字节魔数 `XIDAOEXP`、容器格式版本（uint16），明文头（长度 uint32 加 JSON `{ "encryption": null | 加密参数 }`），然后依次是清单、数据库、草稿附图、离线原图各条目和结束条目；每个条目是类型（uint8）、受管名（长度 uint16 加 UTF-8）、字节数（uint64）与内容。加密文件的明文头之后整体按块加密，解密后的条目布局与不加密文件完全相同。清单为 JSON：容器格式版本、数据库结构版本、导出时的汐岛版本、导出时间（UTC）、包含的类别（离线副本、秘密）、饼干凭据编号序列上界、各类条目数量与总字节、历史条数、发送记录条数与离线副本串数；文件带秘密当且仅当它加密，不一致即拒绝。不加密的文件不另加哈希：数据库由完整性检查验证，附图与原图由声明的字节数核对。读取器按内容判断：魔数、版本、明文头、条目顺序与类型、受管名（不含路径成分）、声明长度与实际内容、清单尺寸、条目数量与总量的上限、清单中的分类统计与实际条目，任一不符即拒绝，解出的内容只写到调用方给定的目录。某类条目的数量或字节一超过清单为该类声明的值，就在写出这一条目之前拒绝，所以解出的内容不会超过清单声明的总量。

### 加密与导出口令

- 带饼干与 App UUID 的导出文件整体加密，只用 Node 内置 `crypto`（`src/main/personal-data/encryption.ts`）：
  - 导出口令（Unicode NFC 规范化后的 UTF-8）经 scrypt 派生 96 字节，分为内容密钥、秘密密钥与校验密钥各 32 字节。每个文件用新的 32 字节随机盐，所以每个文件的密钥不同。参数写在明文头：新文件为 N = 2^17、r = 8、p = 1（约 128 MiB 内存）。读取时参数有上限：N 为 2 的幂且不超过 2^18，r ≤ 16，p ≤ 4，且 128·N·r 不超过 256 MiB；超限的文件在开始派生之前就按“文件已损坏或不完整”拒绝。
  - 明文头之后的内容按每块 64 KiB 明文切分（最后一块较短，不为空），每块用内容密钥做 AES-256-GCM：12 字节随机数是块序号（前 4 字节为 0，后 8 字节为 uint64 BE），附加认证数据是文件中原样的明文头（从魔数到头 JSON 末尾）加 1 字节“是否末块”，每块后跟 16 字节认证标签。块数由文件长度确定，读到的最后一块按末块验证；因此任一字节被改、块被重排或重复、文件被截断或追加内容、明文头被改或口令错误，都会在解密时失败。每块认证通过之后才使用其中的内容。
  - 明文头另记校验值（校验密钥对固定标签的 HMAC-SHA256），用来在读取任何内容之前区分口令错误与文件损坏。
  - 数据库里的每条饼干凭据与 App UUID 还用秘密密钥单独封装（AES-256-GCM，随机 12 字节随机数，附加认证数据为表名与编号），由 main 在快照副本裁剪前写入。所以导出的临时文件、导入的暂存目录里都只有封装后的值，不会出现明文秘密；封装值挪到别的行也无法打开。
- 口令输入两次且一致、不能为空、不限长度、不评估强度。它只从界面单向传入 main，用来派生密钥后即不再使用；密钥只在本次导出或导入期间留在 main 内存中，用完清零；口令与密钥都不写入磁盘、日志或返回值。口令无法找回：忘记口令就不能导入这个文件，对话框写明“忘记口令将无法导入此文件。”。

### 导入个人数据

- 入口是存储与缓存“个人数据”一行的“导入个人数据…”，可用条件与导出相同（只在存储可写时）。打开对话框只列出 `.xidao` 文件，但选中的任何文件都按内容检查；界面拿不到路径，只拿到确认框需要的统计。导入文件是不受信输入。选中文件后，检查期间（包括读取明文头与查询本机系统保护）随时可以取消：取消之后不再弹出口令框或确认框，暂存目录被删除；退出汐岛同样结束检查。
- 确认框出现之前完成全部检查（`src/main/personal-data/import.ts`），任一不通过就拒绝，本机数据与文件都不改动：魔数与容器格式版本、明文头（加密参数及其上限）；文件加密时（带饼干与 App UUID），本机系统保护不可用就直接拒绝（“文件含饼干，但本机无法安全保存，不能导入”，不降级为明文保存），否则先弹出“输入导出口令”，口令错误时在对话框内说明“口令不正确”并可不限次重输，口令正确后才继续检查，每块内容认证通过才写入暂存；清单；数据库结构版本高于本程序支持的版本时，在解出任何内容之前拒绝，并提示“此文件来自汐岛 {版本}，请先升级到该版本或更高版本”；条目名必须是受管名、不含路径成分，声明长度与实际内容一致，清单尺寸、条目数量与总量不超过上限；解出的数据库结构版本与清单一致，并且在 SQLite 运行文件中的任何内容之前（完整性检查、迁移和任何查询都可能执行文件自带的 CHECK、触发器、视图、默认值或生成列表达式），它的每个结构对象（类型、名称、所属表与定义 SQL）都与新安装迁移到该结构版本时完全一致，多一个、少一个或 SQL 不同都拒绝；然后通过 SQLite 完整性检查，在暂存中走同一条迁移链升级到当前结构后结构对象再次与新安装一致，外键检查无误，饼干凭据与 App UUID 的密文都是二进制值且不超过上限（单个 64 KiB、合计 4 MiB、共 10000 行；实际的值不到 1 KiB；只用 SQL 的 `count`／`typeof`／`length` 检查，不读出密文，超限按“文件已损坏或不完整”拒绝，读取秘密时也先做同样检查），数据库记录的草稿附图与离线原图都在且大小一致。解出的内容只写入 `backups/import-staging/`，任何失败都删除它。拒绝的说明为“这不是汐岛导出的文件”“此文件来自汐岛 {版本}，请先升级到该版本或更高版本”“文件已损坏或不完整”“文件含饼干，但本机无法安全保存，不能导入”。具名操作 `personal-data:submit-passphrase`（参数恰好是非空字符串 `passphrase`）只接受主窗口主框架的调用，返回下一步检查结果，不含路径与秘密。
- 暂存所在磁盘的可用空间分两次检查，不足时按“导入失败：磁盘空间不足”失败，删除暂存，不写满磁盘。两次都按磁盘的分配块计算（取卷报告的块大小，得不到时按 4 KiB）：每个文件在其字节数之外再算一整块和一个目录项，因此大量小文件也不会在解出途中占满磁盘。读到清单后、解出任何内容之前，要求能容纳清单声明的全部内容（数据库、各条草稿附图与原图，各按文件计）再加数据库迁移时 SQLite 回滚日志的上限；文件的数据库通过检查后、确认框出现之前，再读取本机数据库，要求能容纳合并时从本机复制到暂存的全部内容：草稿附图与离线原图文件，以及复制进暂存数据库的本机行（目标机保留的表与设置项、饼干凭据与 App UUID、离线副本与草稿各表、离线副本的发言与图片记录），行按每个值的字节数（数字按文本长度）加每值与每行的记录开销估算，表和每个索引各算一份，再按页面至少半满翻倍，只会多算不会少算；另加合并时暂存数据库（检查后的实际大小）的回滚日志上限。本机数据库只在文件通过检查后才读，被拒绝的文件不会碰到它。解出时仍按上文逐类核对声明的条目数与字节数，清单少报内容也不能超出预算。
- 确认框写明导出时间、来源版本、文件包含的类别（有离线副本时含串数，带秘密时加“以及饼干与 App UUID”），以及本机将被替换的浏览历史与发送记录条数；本机的饼干、App UUID、官网登录、离线副本和草稿会保留。按“导入并重新启动”后按钮进入忙碌状态，重复点击无效；准备失败时留在确认框说明“没能准备导入，数据没有改动”。
- 确认后在本次运行中于暂存目录构造导入结果（`src/main/storage/import-staging.ts`，在 worker 线程中执行），本机数据库只读访问；秘密只在 main 中解密（`src/main/personal-data/secrets.ts`），worker 只搬运密文：
  - 以文件中的数据库为底（检查时已迁移到当前结构）。
  - 目标机保留的表与设置行取本机的值。
  - 文件不带秘密时，文件中的饼干凭据与 App UUID 表清空。文件带秘密时，main 用秘密密钥打开每个封装值，再用本机系统保护重新加密：文件中的饼干凭据保持原编号，App UUID 保持原本地编号，指向它们的引用（草稿、各串记住的发言饼干、默认发言饼干与网页同步对象、发送记录、订阅配置）照常可用。
  - 本机的饼干凭据按原顺序追加，在饼干列表中排在文件的饼干之后，编号从“清单中的编号序列上界”与“暂存库已有编号”二者的最大值之后重新分配，自增序列同步推进，之后新导入的饼干也不会用到文件里出现过的编号；“目标机凭据编号映射”记录本机旧编号到导入结果中编号的对应。本机与文件中相同的饼干（按实际发送的 Cookie 值比较，与导入饼干时的重复判断相同）只留文件那一份：本机那份不追加，映射指向文件那份的编号，所以改写到导入结果的本机引用落在文件那份上。本机无法解密的饼干不参与比较，照常追加。文件不带秘密时，文件中的饼干引用找不到对应的饼干，按现有的“已移除，需要重新选择”显示，绝不会落到本机的饼干上。
  - 本机的 App UUID 追加，与文件中值相同的不追加；本地编号已被文件使用（但值不同）的换一个新的随机编号（导入结果中没有引用它）。订阅配置随文件，它使用的 App UUID 在导入结果中（文件带秘密时）就保持已配置、代次不变；不在时，配置回到“未配置”并换用新的配置代次，以前的观察、操作与同步计划留作历史，不会在新代次下继续执行。
  - 离线副本：本机的离线副本追加到导入结果。同一串两边都有时，留更新时间较晚的那份（相同时留文件中的），整份取一边：页、发言与原图都来自同一边；被替换那份独有的原图记录及其暂存文件一并删除。文件没带离线副本时，本机的离线副本全部保留。本机原图复制到暂存的 `images/`，图片记录重新编号；受管文件名已被占用时换一个新名字；文件中已有同一地址的原图时共用那一张。本机原图文件已经不在（或大小与记录不符）时，该图在副本中记为“本地没有保存这张图片”，与导出时的处理相同。
  - 草稿：本机的草稿与它们的附图追加，草稿与附图都按暂存库已有编号（含自增序列）之后重新编号，附图复制到暂存的 `draft-images/`，文件名冲突时改名；附图文件已经不在时，该草稿不带附图。本机草稿的饼干引用按上一步的饼干编号映射改写，因此继续使用本机原来的饼干；本机已经移除的饼干改为一个任何饼干都没有、以后也不会分配的编号，仍显示为“已移除，需要重新选择”。文件中的草稿不受影响。本机的发送记录不保留。
  - 由目标机重建的数据回到初始状态（与导出裁剪相同）：搜索索引在下次启动后补建，提醒检查器重新开始。
  - 导入结果通过外键与完整性检查、数据库记录的草稿附图与离线原图都在暂存中且大小一致后写入换库日志（种类 `import`，记录暂存中全部附图与原图），再经正常退出流程重新启动。
- 退出被现有拦截挡住时（例如有发送的状态无法确认、草稿或工作区没能保存而选择留下），本次导入不生效：删除暂存与日志，确认框内说明原因（如“没有导入：有发送的状态无法确认，数据没有改动。”），本机数据不变。
- 下次启动在打开数据库之前按日志执行（`src/main/storage/import-journal.ts`）：先把当前的 `xidao.sqlite`（连同 `-wal`、`-shm`、`-journal`）和 `draft-images/` 移到 `backups/before-import/`（先在 `backups/before-import.partial/` 汇齐，再替换上一份导入前数据），再把暂存的数据库与草稿附图移到原位，把暂存的离线原图移入 `images/`，删除现有的升级前备份 `backups/pre-upgrade/`，最后清除日志。每一步都可重复执行；中途被中断时，下次启动继续完成；暂存数据在移入之前缺失或不完整时放弃导入，把当前数据放回原位照常打开，提示条说明“导入没有完成，数据没有改动”。日志无法读取或文件系统拒绝某一步时，本次运行不打开数据库，下次启动再继续。导入与恢复升级前备份共用换库日志，已有待执行的恢复时不开始导入。
- 导入后启动沿用现有逻辑：结果未知的发送只读核对、不重新发送，本机没有对应饼干时保持结果未知；未完成的订阅操作转为待核对；`images/` 中导入结果没有记录的缓存图片在启动清理时删除。

### 导入前数据与手动换回

- 被替换的数据（导入前的 `xidao.sqlite` 及其 `-wal`、`-shm`、`-journal` 和 `draft-images/`）保存在用户数据目录的 `backups/before-import/`。它只保留最近一份，下次导入时被覆盖，不会自动删除；界面不显示它的位置，也没有“撤销导入”的入口。
- 手动换回导入前数据：
  1. 完全退出汐岛（托盘菜单“退出汐岛”）。
  2. 在用户数据目录中，把当前的 `xidao.sqlite`、`xidao.sqlite-wal`、`xidao.sqlite-shm`、`xidao.sqlite-journal`（存在的）和 `draft-images/` 移到别处保存。
  3. 把 `backups/before-import/` 中的这些文件和 `draft-images/` 移回用户数据目录，再打开汐岛。导入前离线副本的原图不在导入前数据中：保留到导入结果中且未改名的原图仍在 `images/` 中，其余已被启动清理删除，这些图片会显示为未保存。
- 换回的是导入前的完整数据库：本机原有的饼干与 App UUID 仍是本机系统保护加密的，照常可用；导入带来的饼干不在其中。

### 与升级前备份的关系

- 导入生效时删除现有的升级前备份 `backups/pre-upgrade/`：它保存的是已被替换的数据，留着它，降级后恢复就会悄悄撤销导入。导入前的状态只由导入前数据保存。
- 导入结果在暂存中已迁移到当前结构，换库后打开时不做升级前备份。之后改用较旧版本时，按没有可用备份的只读处理（见“降级与恢复升级前备份”）；要回到导入前，按上一节手动换回。

### 版本与跨平台

- 较新版本照常导入较旧版本导出的文件：文件中的数据库在暂存中走同一条迁移链升级；为此迁移链不得截断，首版样本须始终能导入（见“数据库迁移”）。较旧版本打开较新版本导出的文件时，在解出任何内容之前拒绝并提示需要升级到的版本，不尝试部分导入。
- 导出文件不含平台相关内容：秘密以导出口令加密，不带源机系统保护的密文，导入时用本机系统保护（Windows DPAPI、macOS 钥匙串）重新加密，所以设计上 Windows 与 macOS 之间可以互相导入，本机专用的设置按目标机保留。
- 目前只在 Linux 上验证：存储测试使用两个互不能解密的测试保护器，实际应用在 WSL2 的私有 Xvfb 上使用 gnome-keyring（libsecret）。Windows 与 macOS 上的原生导出导入、两平台之间互相导入、系统保护的重新加密、重启换库时进程退出与单实例锁的顺序，以及原生保存／打开对话框，都尚未原生验证。

## 验证要求

发布验证使用本地受控 HTTP、真实 SQLite／附件目录与 Electron 窗口：覆盖正文和附图、PO 三选择、失败存稿、响应丢失及结果落盘前进程中断，重启后无自动重投。单元／集成测试还覆盖总时限、重复入口、回读不符、数据库事务回滚和未知稿锁定。此范围不等于当前客户端在真实论坛的发布验收；线上写入仍须单独取得测试对象与额度授权。Linux 演练的合成密钥保护不证明 Windows DPAPI 或 macOS 钥匙串行为。

预览与页面交互的验证需使用 `npm run build` 的生产 CSS，而不只看开发热更新：同一组多行、空行、允许格式、防剧透、附图及缺失字段样本应覆盖各类串列表入口（版面、时间线、订阅、提醒、离线、历史和同步预览），并检查浅／深色、舒适／紧凑、窄窗和 200% 缩放的代表组合。页面次要按钮需实走 Tab、点击、Enter、Space、表单回车和忙碌重复输入；草稿删除／撤销核对真实 SQLite 与附件，订阅离线入口核对同一副本和任务、回焦及订阅集合不变。受控网络记录用于确认历史／同步预览没有额外逐串读取或原图预取。这些应用层检查不代替 Windows／macOS 原生安装、升级、系统密钥保护及数据连续性验收。

复制原图的应用层检查覆盖工具栏、Ctrl／Cmd+C、图片右键与 ContextMenu 键／Shift+F10 入口，忙碌时重复触发只执行一次且焦点不丢；查看器内选中文字时 Ctrl／Cmd+C 仍复制文字。样本至少包括透明静态图、超出窗口的长图和两帧内容不同的动图，并在复制后关闭查看器、清理缓存再粘贴。Electron 文档只说明接口可用，不证明接收软件的兼容性；Windows 与 macOS 的文件剪贴板格式不同，不能互相推断。

Windows x64（系统构建 26300、Electron 45.0.0）已在 QQ 9.9.30.48517 与微信 4.1.15.56 的受控输入区观察：320×240 静态图以图片接收，QQ 透明显示正常，微信透明度无法确认；240×2400 长图均以图片接收且顶底完整；160×120 红蓝两帧 GIF 在关闭查看器并清理普通缓存后，仍以图片接收并在输入预览中交替播放。正常退出、重开同一应用数据目录而不重新复制后，两软件输入预览仍能播放；改为复制静态图后，旧动图受管文件已回收。启动与运行中清理还验证了保留当前原生文件引用、回收孤立文件与中断临时文件、不删除非受管文件。系统剪贴板 PNG 的尺寸与 alpha 0／128／255 另经原生读回确认，不替代微信的透明显示证据；GIF 文件原字节与样本相同。

Apple Silicon macOS 27.0（26A428、arm64、Electron 45.0.0）已用 Node 24.22.1 原生构建并运行，同一组静态透明图、长图、两帧 GIF 在 QQ 6.9.78（build 36350）、微信 4.1.13 中完成了人工复制／粘贴检查，得到三类样本整体通过的反馈；这轮反馈未逐软件单列透明效果、图片或文件附件形态、动画预览细节，也未报告人工重开后再次粘贴的结果。Mac 系统剪贴板另确认了完整 PNG 尺寸与 alpha、原 GIF 字节一致，以及原生 `NSFilenamesPboardType` 文件引用；关闭查看器、清理缓存、正常退出／重开、启动残留回收与静态图替换均保留应保留的文件并回收旧副本。Command+C 也已在受控应用窗口实际触发复制。这些系统与资源校验不替代未单列的接收软件显示细节。

两平台均只在受控输入区粘贴，未发送消息，不证明收件端显示。Intel macOS 尚无本功能的原生运行证据，不能从 Apple Silicon 运行推断物理 Intel 已验收。
