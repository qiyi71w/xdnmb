# 开发与维护

面向参与开发和发布的维护者。使用说明见 [README](../README.md)。

## 环境与命令

需要 Node.js 24 LTS 与 npm（版本见 `.nvmrc`；`.npmrc` 启用了 `engine-strict`）。

源码注释直接说明行为与约束，不依赖未公开的规格章节编号；需要交叉引用时，指向仓库内的公开文档或源码。

```bash
npm ci            # 安装锁定依赖
npm run dev       # 开发模式（热更新）
npm run build     # 构建到 out/
npm start         # 运行构建产物
npm run typecheck # 主进程、preload、共享代码、界面与统计服务的类型检查
npm test          # Vitest，运行在 Electron 自带的 Node 中，与应用使用同一 SQLite 驱动
npm run dist:win  # 在 Windows 上构建 x64 NSIS 安装程序与 latest.yml 到 dist/
npm run dist:mac  # 在 macOS 上构建 x64／arm64 DMG 与 latest-mac.yml 到 dist/（DMG 由 hdiutil 生成，只能在 macOS 上构建）
npm run analytics -- serve  # 本机运行使用统计服务（配置见 docs/analytics-service.md）
```

## 打包与发布

打包配置见 `electron-builder.yml`：使用上游预编译 Electron，不编译 Chromium／Electron／Node；better-sqlite3 自带各平台的 N-API 预编译模块，打包时不需要编译原生代码。只打包 `out/`、`resources/icons/`、`package.json` 与 `LICENSE`。版本号取自 `package.json`；发布时把安装包与对应的 `latest.yml`（Windows）、`latest-mac.yml`（macOS，两种架构合在一个文件里）一起上传到 tag 为 `v<版本>` 的正式 GitHub Release，客户端依赖这些文件名与其中的 SHA-512。

`.github/workflows/macos-packages.yml` 在 GitHub 的 Apple Silicon macOS 机器上运行类型检查和测试，构建两种架构的 DMG，再用 `scripts/ci/mac-update-smoke.mjs` 检查：两个应用的 CPU 架构与 SQLite 原生模块、应用身份、图标、临时签名、`latest-mac.yml` 中的 SHA-512；Intel 版在 Rosetta 下能启动并读写数据；Apple Silicon 版安装后，用只在更新网络会话内应答的受控发布源走完缺少元数据时检查失败（不显示为已是最新）、发现新版、校验失败丢弃、自动下载、打开 DMG、退出、按用户方式替换应用、下次启动显示新版本并保留设置。结果不依赖仓库实际发布了哪些 Release。DMG、检查记录和应用输出作为工作流产物保留 14 天，不发布 Release。这些是自动化检查，不包括 Gatekeeper 首次打开提示与钥匙串授权等需要真人操作的环节。

## 数据与安全实现

- 本机数据保存在 Electron 用户数据目录下的 `xidao.sqlite`，由主进程中的单个数据库 worker 访问（WAL、外键、短事务）。数据库结构单向升级；升级失败时回滚并保留原文件，不删除或重建数据库。用较旧版本打开由较新版本写入的数据库时，以只读方式读取并拒绝写入（此时也不能导入、重命名、移除饼干或修改用途）。
- 阅读模式、阅读位置、访问记录和设置是个人记录，与缓存的论坛内容分开保存，不依赖缓存内容存在。汐岛不提供串收藏，也不记录已读／未读：没有首条未读、全部标为已读、未读数或“仅未读”筛选，订阅列表不显示新回复，追更请开启提醒。收藏版块（图标栏首字入口与版块管理）不受影响。自己的发言、PO 饼干与引用我的发言都只按饼干 ID 识别，不另存发言库。
- 读取到的图片保存在用户数据目录下的 `images/` 中，文件名由应用生成，数据库记录每个文件是缩略图还是原图、来源地址、取得时间、实际格式与尺寸，缩略图与原图分别记录。同一图片被多条发言或多个标签使用时只保存一份。
- 图片先完整写入临时文件，校验后改名到位，再提交数据库记录；中途失败、取消或写库失败时，已有的文件和记录保持不变，新文件被删除。正在显示图片的阅读视图会保护所用图片不被清理；清理只删除没有任何保护的记录及其文件，不会删除 `images/` 以外的文件，也不跟随符号链接。每次启动时会移除上次中断留下的临时文件和没有记录的文件。界面通过应用自己的 `xidao-image://` 地址读取这些文件，不暴露文件路径。
- 普通缓存的图片在超过额度或手动清理时按上面的规则删除；受保护（正在显示、离线副本引用、草稿副本）的图片不会被删除。
- 复制原图只针对查看器中已完整解码显示的原图：界面只传发言编号和该原图的 `xidao-image://` 地址，主进程核对它确是这条发言已取得的受管原图后自己确定文件与编码，不接受任意路径，不重新下载，也不以缩略图代替。复制期间对该原图另加临时保护，结束即释放，不改变阅读视图、离线副本或草稿对它的保护。文件以不跟随符号链接的单个句柄读取，按内容识别格式，并在无预加载、不能打开新窗口的隐藏沙箱页面中逐帧完整解码，尺寸须与文件头一致。
- 静态图写入完整解码后的 PNG 图像，保留透明通道，不缩放、不按窗口裁切。动图不转成静态图：原始字节复制到用户数据目录下单独的 `clipboard-images/`，再以文件 URI 列表写入剪贴板（Electron [`clipboard`](https://github.com/electron/electron/blob/v45.0.0/docs/api/clipboard.md) 与 [`ClipboardItem`](https://github.com/electron/electron/blob/v45.0.0/docs/api/clipboard-item.md) 的 `text/uri-list`，在 Windows／macOS 上对应系统文件剪贴板），接收软件可能把它作为文件附件。内容准备好后一次提交，不先清空剪贴板；原图未就绪、文件校验未通过、另一次剪贴板操作进行中或写入失败时如实说明，不报告成功。
- `clipboard-images/` 与图片缓存分开：关闭查看器、普通缓存额度或手动清理都不会删除其中文件，退出、重启后剪贴板仍引用的文件继续保留。主进程在启动时、此后每 30 秒、每次复制成功后以及退出时回收这个目录：只读取剪贴板中的文件引用（不读取文字或其他内容），保留仍被引用的文件，删除其余文件和中断留下的临时文件；剪贴板被其他内容替换后，旧文件在下一轮删除。回收不跟随符号链接，不触及 `images/`；剪贴板暂时无法读取或文件仍被占用时本轮不删除，留到下一轮。
- 草稿保存在数据库中：每份草稿只有一个保存版本，目标、饼干引用、文字字段与附图引用在同一事务中一起替换；保存失败时上一个保存版本保持不变。饼干引用不随饼干移除而改写，移除后显示为“已移除”。各串记住的发言饼干同样只保存本地引用。
- 附图由主进程通过系统选择框读取所选文件，先复制为同目录临时文件，按文件内容确认是 JPEG、PNG、GIF 或 WebP 并检查尺寸，再改名为用户数据目录下 `draft-images/` 中的受管副本；所选原始文件只读不改。源文件不可读、不是图片、尺寸过大、磁盘空间不足都会作为失败说明，不留下临时文件。界面通过 `xidao-image://draft/…` 显示副本。
- 副本在被已保存草稿、打开中的编辑、仍可撤销删除的草稿或发送中／结果不明的发送尝试引用时受保护；没有任何引用时删除记录与文件。每次启动先恢复发送尝试，再清理无引用副本及中断留下的临时文件；尚未自动保存的编辑及其附图不跨重启保留。结果不明尝试的附件不会被启动清理移除。
- 饼干 userhash 通过 Electron `safeStorage` 的异步接口加密后存入数据库（Windows 为 DPAPI，macOS 为钥匙串）；数据库只保存显示名称、公开的饼干 ID、本地编号与密文。系统保护不可用时（包括 Linux 在没有密钥环服务时的 `basic_text` 后备）拒绝导入，已保存的饼干保持密文、不能用于读取，不会改用明文保存。系统保护防的是数据库文件被直接读取，不能防住以同一登录用户身份运行的其他程序。
- 解密后的 userhash 只在主进程内存中使用：界面只能取得显示名称、饼干 ID、来源、导入时间和用途选择；粘贴内容只在导入时经 IPC 传入主进程一次，导入成功或关闭设置后清空输入框。饼干只附加在主进程发往论坛阅读、订阅和发布接口的请求上，不写入 Chromium 会话 Cookie，因此界面加载的图片、外部链接等不会携带它。
- App UUID 使用相同的系统密钥保护器，数据库中只有本地引用和密文；更换后保留旧引用对应的密文供固定操作核对及显式合并，常规查询不返回秘密或秘密片段。观察、配置代次、逐项意图／报告、同步基线及计划历史保存在独立表中，不随读取失败清除。
- 订阅普通刷新按集合与固定配置代次共用在途读取，离开页面不取消共享任务；显式停止只停止该次读取，不重试。最新读取任务、最后完整展示快照和成员证据分别消费同一份观察记录。完整性须由从第 1 页连续读到有效空页证明，旧记录中的 `valid_observation_json` 只表示可用页，不证明完整；因此旧部分观察不会在升级后变成未订阅的证据。展示快照不用于确认写入或推导同步删除，写入回读和同步执行前复核仍使用固定对象的新证据。
- 待核对操作的 `dismissedAt` 是独立的本地持久关闭时间，旧 JSON 缺字段时视为未关闭，不改变 schema 或历史报告。关闭事务成功后才解除该对象／串的待核对保护；失败保留原记录，运行中写入或核对拒绝关闭。关闭不访问远端、不删历史、不推导当前成员状态，后续写入仍须明确用户操作。
- 发送意图和结果由数据库事务保存；确认结果、实际发言身份、来源草稿删除在同一事务中完成。意图保存失败时不会发送；发送后的结果写库失败则保留原意图，界面说明可能已经发出，重启按未知处理。发送记录保存正文与身份的本地编号，不保存解密后的 userhash。退出时，已开始的发送只等到原本的 60 秒时限，结果写入本地存储后才结束进程。
- 全串／PO 的本机回复排除只使用既有第1页请求，不补读末页。只有新鲜页面的回复序列完整、无重复／异常且填满该页应有的计数槽时，才保留该模式前19条的序号；不会从全站串号、时间或同饼干推算序号。模式计数增长区间、规则代次、清零状态和本机确认回复的处理结果属于个人记录，不随普通缓存清理。确认和计数路径都在同一SQLite事务中消费可靠证据；晚确认只能修正仍属于该回复的区间，已清零的区间不抵扣后续增长。通知决策读取当前轮修正后的有效增长，已经投递的通知不撤回。长串未见目标、删除缺槽或计数回退后的证据不足时，保持正常计数／通知与待处理事实，允许仍提醒自己的回复；不为等待归属延后他人通知。
- 界面页面启用 sandbox 与 context isolation，禁用 Node 集成与 webview，使用严格 CSP；不允许页面导航到其他地址或打开新窗口。权限仅为应用自己的主页面开放按需读取本机字体，其他权限均拒绝；官网登录窗口拒绝所有权限。界面只能调用少量具名操作，主进程校验调用页面（仅主窗口主框架中的应用页面）与参数，不提供任意网址、SQL 或文件访问。
- 剪贴板只经两类具名操作：对发起请求的窗口执行剪切、复制、粘贴、全选之一，或写入应用给定的纯文字（复制串号、复制内容、复制饼干、复制选中文字，长度有上限）；以及上面的复制原图。界面不读取剪贴板内容，粘贴由主进程直接作用于焦点所在的输入框；剪贴板权限没有因此对页面开放。
- 应用只运行一个实例；再次启动会唤起已运行的窗口。

### 启动公告

- 公告服务只读取固定 `https://nmb.ovear.info/nmb-notice.json`，专用传输无凭据来源、不跟随重定向，总超时 10 秒，压缩与解压响应各限 128 KiB。冷启动后台读取一次，窗口恢复不触发读取；设置中的主动重试共用在途请求。
- `enable` 必须为布尔值；仅 `true` 且安全解析后有可见正文才能自动展示。`date` 保留完整字符串或安全整数，不截成日期；抑制身份直接比较完整 `date` 与原始正文，同日期正文修订可再次提示。正文复用受限解析与展示，不执行 HTML，不加载外部图片；引用只在明确点击后定位，不因展示或悬停预取。
- 最近公告与抑制选择一起保存在现有 `settings` 表的独立 `announcements` 行，无 schema 变更；普通缓存清理和其他设置更新不覆盖该行。写入串行化，“不再提示”持久化成功后才关闭；失败可继续关闭本次提示，不伪报已保存。初始记录不可读时不覆盖未知选择，也不自动弹窗。
- main 原子发放一次自动展示资格，并检查原生窗口可见、未最小化且聚焦；renderer 还须等工作区与启动发送恢复检查完成，避开编辑器、其他模态、输入焦点和发送操作。迟到结果保留等待，不夺取现场。网络或协议失败保留本地副本供主动查看，不以旧副本自动弹窗。
- 聚焦验证覆盖真实临时 SQLite 重开、只读失败、清理保留、写入竞争、IPC 调用方与参数边界。Linux 实际 Electron 验证延迟响应与恢复编辑器、关闭／抑制／同日期修订、主动重试、键盘焦点、浅深色及窄窗 200% 缩放；这些证据不替代 Windows／macOS 原生验收。

### 联网搜索与串号定位

- 每个搜索历史条目按 `xds`／`nmb-search` 隔离查询链、结果页和请求代次。切换只恢复现场；只有提交、翻页和主动重试才能联网。旧响应只能落在原条目／渠道，旧查询不得覆盖新查询。失败保留已取得结果，不自动换服务、预取或重试。
- XDS 请求固定到 `https://xds.wol.moe/api/v1/search` 与显式 `/api/v1/thread-of/<串号>`，UA 由 `app.getVersion()` 生成 `Xidao/<version>`；不借用其他版本绕过服务白名单。nmb-search 仍使用 `/api/v1/web` 与最多发送一次的 `npt`；取消或响应丢失不重放令牌，已取页保留。XDS 页码失败可由用户重试，不能把它当作消耗式 token。
- 两个传输各自限定来源、拒绝重定向、限制压缩／解压体积和总等待时间，均没有可携带凭据的来源。主进程不接收 renderer 给出的服务 URL 或身份字段。服务的 `Retry-After` 只形成对应渠道的运行期截止时间，不臆测每日额度或请求间隔；关闭或重开搜索页不解除仍有效的截止时间。
- XDS 的普通空结果、降级查询、HTTP 错误、验证要求和限流分别处理。响应中的文本只作为有界纯文本，XDS 结果 URL 由经过字符串校验的串号构造，不使用服务任意给定的目标。JSON 整数串号从原始数字文本读取，避免超过安全整数范围后的舍入。
- `onlineSearchChannel` 使用已有 SQLite settings 读写和逐项校验；缺失／无效取 `xds`，已有明确值保留，无须 schema 变更。它不改变搜索页初始“本机”侧，也不作用于本机筛选和串内搜索。
- 显式串号输入与正文引用共用 1–20 位正十进制字符串校验；论坛链接的 `r`／`page` 只是待验证线索。所属串反查不等于精确位置：只有既有阅读定位核实成功才能提交目标导航，只有所属串时保留明确“打开原串”路径，不遍历整串猜页码。失败不修改历史或创建空标签。
- 正文 `No.` 使用带 `readingOnly` 标记的安全 `quoteRef` 节点；提醒引擎只消费原有明确引用，便利阅读识别不扩大后台引用请求。裸数字保持文本，正文、引用卡和版规／说明共用完整有效选区的动作校验。卡片内选区替换预览时沿用原触发点或外层选区，不保留被替换正文的失效 Range；失败不提交导航，关闭后归还可恢复的来源焦点。


## 数据库迁移

- SQLite schema v8 按实际表结构归并早期订阅、同步计划、草稿／发布、保留内容与工作区；v9 追加提醒，v10 追加搜索派生表、FTS5 trigram、事务投影与逻辑字节核算；v11 给饼干加入列表顺序，并把原“浏览饼干”用途并入顺序（原浏览饼干排到首位）。迁移单个事务完成并保留个人记录。已知早期 v2 且已有 `credentials` 表的数据库无法升级；早期独立搜索开发分支的同号 v8 库缺少这条历史所需的发布／工作区表，也会拒绝升级并保持原文件不变。升级前应备份数据库，不把版本号相同当成结构相同。
- SQLite schema v12 追加独立账号会话表，只接收非空 BLOB 密文与到期时间；账号会话不参与浏览／发言／网页订阅身份选择。v13 追加本机屏蔽表（串号或饼干标识），只在本机使用，不发送到论坛。v14 在同一迁移事务中删除串收藏、逐条已读记录与关注起点三张表，不迁移其中的数据；阅读位置、访问记录、提醒及其补查所用的页观察与末尾观察保留。v15 给饼干加入可空的饼干 ID 列（升级前的饼干为空），并删除“我的发言”记录表；发送尝试、结果状态与确认到的编号保留在发送记录中。
- v16 把提醒改为回复数基线：保留每条提醒规则、是否开启及其代次（原起点时间作为最近开启时间），删除旧的起点与水位、补查覆盖、检查轮次、逐事件提醒、通知登记和末尾观察，不做转换；新增按串、按提醒种类保存基线、已核对编号与计数的表，以及上次检查时间。升级后的第一次检查只为所有开启的规则重建基线、不计数。迁移在单个事务中完成，失败时原库保持不变；换回旧版本时不承诺能读取新的提醒数据。
- v17 给提醒检查器追加退避间隔、限流事件、已通知与已确认状态，保留 v16 的规则、基线与计数；迁移失败时在事务内回滚，不清空提醒。运行中写库失败时，当前进程仍保守延长限流间隔，确认或解除通知状态须写入成功后才生效；尚未写入的新退避不能保证在重启后保留。
- v18 删除草稿表的 E-mail 列，草稿的目标、饼干、标题、名称、正文、水印与附图保留；已有发送记录中保存的原始载荷不改写，其中的 E-mail 不再显示或使用。迁移在单个事务中完成，失败时原库保持不变；不承诺旧版本能读取升级后的数据库。
- v19 给发送尝试加入发送时的饼干 ID，并允许失败原因记为“可能已发出、核对未找到”；只有发送中与结果不明的尝试锁定来源草稿。已有尝试的饼干 ID 取升级时该饼干（本地编号不复用）已知的饼干 ID。SQLite 不能就地修改约束，因此在同一迁移事务中重建该表，保留全部尝试、编号与不复用的编号计数。迁移失败时回滚，原库保持不变。
- v20 新增饼干颜色表，保存饼干 ID、颜色名称与添加时间，并记下已自动标过导入色（蓝）的饼干 ID。升级时为已导入且饼干 ID 已知的饼干补标一次蓝色（添加时间取该 ID 最早的导入时间）；饼干 ID 未知的饼干不标，之后补上 ID 时再标。迁移在单个事务中完成，失败时原库保持不变。
- v21 给发送记录追加可空的论坛提示列（明确失败时论坛页面中 `<p class="error">` 元素的文字，最多 120 字），已有记录不改写、读作没有论坛提示；单个事务完成，失败时原库保持不变。
- v22 追加提醒计数增长区间、模式内回复序号证据和本机已确认回复的一次性处理记录，并给规则状态加入序号可信标记。保留已有规则／代次、基线、计数、发送确认、身份、阅读位置和缓存保护关系；既有计数不伪造历史区间，旧确认先作为待处理事实。迁移和后续计数修正均按事务回滚，失败不清库。计数变小会使当前规则代次的序号空间不再可信，继续正常回复数提醒但不再据其排除本机回复；关闭再开启规则建立新的基线和证据。旧版本不能写入此schema，降级需使用升级前备份。
- v23 让饼干颜色条目可以处于“默认”：颜色列改为可空，空值表示随主题的普通饼干 ID 文字色，与有颜色的条目、已删除（无行）的 ID 分开。SQLite 不能就地去掉 NOT NULL，因此在同一迁移事务中重建该表，保留全部条目的颜色、添加时间（即列表顺序）和饼干 ID；自动标色记录与饼干凭据不改动，v22 的提醒证据表保持不变。迁移失败时回滚，原库保持不变。界面上原来的“清除颜色”由“默认”取代，“删除”才移出列表；手动添加的条目为默认，自动标色只对每个导入的饼干 ID 生效一次，改成默认或删除后不会再被补成蓝色。此版本不认识的颜色名读作默认。
- 从支持离线删除的 v15 数据库升级到 v17 时，已有离线副本和已转入普通缓存的内容沿用各自保留关系；已删除的副本不会因升级恢复。删除离线副本不清零提醒计数、不关闭规则，也不重置限流退避。升级前正常退出应用并备份用户数据目录；需要降级时恢复与旧版本匹配的升级前备份，不把旧程序读取新 schema 当作数据回滚。

## 验证要求

发布验证使用本地受控 HTTP、真实 SQLite／附件目录与 Electron 窗口：覆盖正文和附图、PO 三选择、失败存稿、响应丢失及结果落盘前进程中断，重启后无自动重投。单元／集成测试还覆盖总时限、重复入口、回读不符、数据库事务回滚和未知稿锁定。此范围不等于当前客户端在真实论坛的发布验收；线上写入仍须单独取得测试对象与额度授权。Linux 演练的合成密钥保护不证明 Windows DPAPI 或 macOS 钥匙串行为。

预览与页面交互的验证需使用 `npm run build` 的生产 CSS，而不只看开发热更新：同一组多行、空行、允许格式、防剧透、附图及缺失字段样本应覆盖各类串列表入口（版面、时间线、订阅、提醒、离线、历史和同步预览），并检查浅／深色、舒适／紧凑、窄窗和 200% 缩放的代表组合。页面次要按钮需实走 Tab、点击、Enter、Space、表单回车和忙碌重复输入；草稿删除／撤销核对真实 SQLite 与附件，订阅离线入口核对同一副本和任务、回焦及订阅集合不变。受控网络记录用于确认历史／同步预览没有额外逐串读取或原图预取。这些应用层检查不代替 Windows／macOS 原生安装、升级、系统密钥保护及数据连续性验收。

复制原图的应用层检查覆盖工具栏、Ctrl／Cmd+C、图片右键与 ContextMenu 键／Shift+F10 入口，忙碌时重复触发只执行一次且焦点不丢；查看器内选中文字时 Ctrl／Cmd+C 仍复制文字。样本至少包括透明静态图、超出窗口的长图和两帧内容不同的动图，并在复制后关闭查看器、清理缓存再粘贴。Electron 文档只说明接口可用，不证明接收软件的兼容性；Windows 与 macOS 的文件剪贴板格式不同，不能互相推断。

Windows x64（系统构建 26300、Electron 45.0.0）已在 QQ 9.9.30.48517 与微信 4.1.15.56 的受控输入区观察：320×240 静态图以图片接收，QQ 透明显示正常，微信透明度无法确认；240×2400 长图均以图片接收且顶底完整；160×120 红蓝两帧 GIF 在关闭查看器并清理普通缓存后，仍以图片接收并在输入预览中交替播放。正常退出、重开同一应用数据目录而不重新复制后，两软件输入预览仍能播放；改为复制静态图后，旧动图受管文件已回收。启动与运行中清理还验证了保留当前原生文件引用、回收孤立文件与中断临时文件、不删除非受管文件。系统剪贴板 PNG 的尺寸与 alpha 0／128／255 另经原生读回确认，不替代微信的透明显示证据；GIF 文件原字节与样本相同。

Apple Silicon macOS 27.0（26A428、arm64、Electron 45.0.0）已用 Node 24.22.1 原生构建并运行，同一组静态透明图、长图、两帧 GIF 在 QQ 6.9.78（build 36350）、微信 4.1.13 中完成了人工复制／粘贴检查，得到三类样本整体通过的反馈；这轮反馈未逐软件单列透明效果、图片或文件附件形态、动画预览细节，也未报告人工重开后再次粘贴的结果。Mac 系统剪贴板另确认了完整 PNG 尺寸与 alpha、原 GIF 字节一致，以及原生 `NSFilenamesPboardType` 文件引用；关闭查看器、清理缓存、正常退出／重开、启动残留回收与静态图替换均保留应保留的文件并回收旧副本。Command+C 也已在受控应用窗口实际触发复制。这些系统与资源校验不替代未单列的接收软件显示细节。

两平台均只在受控输入区粘贴，未发送消息，不证明收件端显示。Intel macOS 尚无本功能的原生运行证据，不能从 Apple Silicon 运行推断物理 Intel 已验收。
